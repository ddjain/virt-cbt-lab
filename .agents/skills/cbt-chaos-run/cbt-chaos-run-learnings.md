# CBT Chaos Run Learnings

Reusable, evidence-backed guidance for planning and troubleshooting CBT Chaos scenario execution. This file is separate from issue-triage learnings so the run skill loads only knowledge relevant to execution.

## How to maintain this file

- Read before planning a run or triage.
- Add a dated entry only when the current execution or investigation establishes a reusable, actionable lesson.
- Include the affected scenario/stage, observed issue, resolution or validated workaround, and sanitized repository-relative evidence path(s).
- Keep entries concise and generally applicable; keep run-specific findings in the scenario's run report and issue-specific decisions in its artifacts.
- Never include secrets, credential values, private hostnames, environment-specific absolute paths, or unsupported speculation.
- When newer evidence invalidates a lesson, correct or remove the stale guidance rather than accumulating contradictory advice.
- Add entries only after the run closeout confirms an important, generalizable learning; check for duplicates first and prefer updating an existing entry.
- Do not create a new learning file. If no appropriate existing file exists, ask before creating one.
- If a learning implies changing a main skill, propose the exact change and get user confirmation before editing that skill.

## Learnings

- **2026-10-09 — CBT-F-01 compute-log observer:** The installed OpenShift client rejected `oc logs --follow --tail=all` because `--tail` requires an integer. A corrected `--tail=-1` stream captured replacement-launcher logs, but the initial observer missed the primary signal during a target-listing gap. Validate `oc logs` flags against the installed client and arm the exact-label log stream before backup creation. Evidence: `cbt-chaos/scenarios_v2/CBT-F-01/runs/20261010-cbt-f-01-r02/observer/watch-compute-stream.log` and `watch-compute-corrected.log`.

- **2026-10-10 — watches for not-yet-created resources:** `oc get <kind> <name> -w` returns NotFound before a run-owned object exists; retry loops add sequential API polling. Use a persistent watch filtered by `metadata.name=<exact-name>` and validate that the installed client keeps it open before creation. CBT-F-02 used this to arm exact backup/tracker/PVC watches before the run. Evidence: `cbt-chaos/scenarios_v2/CBT-F-02/runs/20261010-cbt-f-02-r01/observer/observer.sh`, `backup-watch.raw`, and `reconciliation.txt`.

- **2026-10-10 — Krkn exact pod-name recovery matching:** `pod-scenarios` can report the deleted pod as unrecovered when its ReplicaSet replacement has a new name, even after the controller Lease moves and the Deployment returns to 2/2 Ready. Verify Lease handoff, replica readiness, and replacement identity independently; treat Krkn recovery status as separate from CBT product evidence. Evidence: `cbt-chaos/scenarios_v2/CBT-F-03/runs/20261010-cbt-f-03-r02/observer/independent-finding.txt` and `trigger.log`.

- **2026-10-10 — Krkn resiliency parser warning:** In CBT-F-01, `pod-scenarios` completed with exit status 0 and the run-scoped observer confirmed the exact disruption, but Krkn output also said `Failed to parse resiliency report: marker not found in logs`. Preserve the raw output and corroborate target/action/timing from Kubernetes watches; treat the parser warning separately from chaos execution and investigate output-format compatibility. Evidence: `cbt-chaos/scenarios_v2/CBT-F-01/runs/20261010-cbt-f-01-r03/logs/trigger.log` and `observer/finding-20261010T034832Z.txt`.

- **2026-10-10 — restore-helper PodSecurity warning:** Both same-VM and supplemental restore runs warned that the restore helper used privileged/hostPath settings not accepted by the `restricted` policy, even though their restore checks completed successfully. Treat this as a harness security-policy warning, not a CBT backup failure; verify the required SCC is explicitly approved or make the helper compatible with the cluster policy. Evidence: `cbt-chaos/scenarios_v2/CBT-F-01/runs/20261010-cbt-f-01-r03/e2e/same-vm-recovery.log` and `runs/20261010-cbt-f-01-r03-recovery/e2e/supplemental-clean-lifecycle.log`.

- **2026-10-10 — per-run workload overrides must be make arguments:** `make e2e` runs through the checkout's `.env` (`-include .env`), whose assignments override environment-prefix variables; exporting `GUEST_INCREMENTAL_FILE_COUNT=500` before `make e2e` was silently beaten by `.env`'s 1000 and only the pipeline-config printout revealed it. Pass per-run workload overrides as make command-line arguments (e.g. `make e2e … GUEST_INCREMENTAL_FILE_COUNT=500`), which do take precedence, and confirm the value in the printed pipeline configuration before interpreting results. Evidence: `cbt-chaos/scenarios_v2/CBT-F-01/runs/20261010-cbt-f-01-r04/recovery-lifecycle.log` (1000 printed despite 500 exported) and `rec500-lifecycle.log` (corrected run).

- **2026-10-10 — live-watch readiness requires API proof:** A CBT-F-01 observer wrote its armed marker while child `oc` watches lacked exported `KUBECONFIG`; they emitted configuration errors and no target/signal records, so the injection remained BLOCKED despite later UID-matched Kubernetes termination events. Export the host-local kubeconfig into every watcher, require a successful scoped API read and live watcher health before acknowledging “watch armed,” and abort injection if either fails. Evidence: `cbt-chaos/scenarios_v2/CBT-F-01/runs/20261010-cbt-f-01-r05/observer/independent-baseline-pods.stderr`, `independent-pods-watch.jsonl`, and `finding.md`.
- **2026-10-10 — compute-log observer startup:** In CBT-F-02, the launcher Pod appeared before its `compute` container was ready; the initial `oc logs --follow` request returned `PodInitializing`, and the observer did not establish the `Backup started` signal before the Full backup completed. Wait for the exact Pod UID and a Ready compute container before following logs; if log startup returns `PodInitializing`, retain the exact Pod watch and retry only after revalidating the same Pod/container identity. Treat the log observer as armed only after its stream is healthy. Evidence: `cbt-chaos/scenarios_v2/CBT-F-02/runs/20261010-cbtf02-9d5f/observer/compute-log.watch.jsonl.stderr`, `final.pod.json`, and `final.vmbackup.json`.
- **2026-10-10 — dynamic pod-event readiness at injection:** In CBT-F-02, the exact `Backup started` signal and launcher identity were captured, but the trigger remained fail-closed because the target-Pod event watch was not ready at the action boundary. Start the run-scoped events watch as soon as the launcher UID is resolved, using field selector `involvedObject.name=<exact-pod-name>`; prove authorization, ready marker, live PID, and empty stderr before the backup window. Evidence: `cbt-chaos/scenarios_v2/CBT-F-02/runs/20261010-cbtf02-0c9a/trigger-console.log`, `observer/trigger-signal.json`, and `observer/PRESERVED`.
- **2026-10-10 — container-signal effect verification:** In CBT-F-02, an in-container signal-9 request to PID 1 in `compute` returned status 0, but the same Pod UID/container ID, restart count 0, Ready/Running state, and absence of a post-request Pod event showed no independent container effect; the Full backup succeeded. Treat `oc exec` completion as request evidence only. Require a target-specific postcondition before calling container disruption valid; this run did not validate an alternative action. Evidence: `cbt-chaos/scenarios_v2/CBT-F-02/runs/20261010-cbtf02-3b88/action-result.json`, `observer/FINAL`, `observer/post-action-compute-inspection.txt`, `observer/events-pod.watch.jsonl`, and `observer/terminal-vmbackup.json`.

- **2026-10-10, updated 2026-10-11 — observer pre-creation vs. trigger fail-closed guard:** The CBT-F-02 trigger originally fail-closed when `runs/<RUN_ID>/` already existed, so an observer that pre-creates that directory for its watch output blocked the run before it started; the first workaround was to stage observer files in a temporary location and move them in after the trigger created the artifact directory. The staging move is safe for live watches: renaming the whole `runs/<RUN_ID>/` directory to a sibling staging path preserves the watchers' open file descriptors, so the observer can keep recording through the move and restore its files under the trigger-created run dir afterwards (validated in CBT-F-04 on 2026-10-11). As of 2026-10-11 the CBT-F-02 trigger guard explicitly allows a pre-existing `runs/<RUN_ID>/` whose sole entry is the read-only `observer/` subtree and still blocks any other pre-existing content, so an observer may create `runs/<RUN_ID>/observer/` directly before the trigger starts; other scenario triggers (e.g. CBT-F-04) still fail-close on any pre-existing directory, so no cluster mutation occurs if the guard fires. Verify the active trigger's guard before choosing either approach. Evidence: `cbt-chaos/scenarios_v2/CBT-F-04/runs/20261011-cbtf04-ctrl-restart-r01/observer/` (watches stayed live across the staging rename) and `cbt-chaos/scenarios_v2/CBT-F-02/runs/20261010-cbtf02-m3r8/`.

- **2026-10-10 — comment edits can delete load-bearing trigger code:** A documentation-only edit to the CBT-F-02 trigger's comment block consumed the `TRIGGER_CMD=` assignment line sitting inside the replaced range (earlier edits had shifted line anchors), and `bash -n` passed because the script only failed at runtime under `set -u` ("TRIGGER_CMD: unbound variable") — after the E2E had already started, so the backup completed with no chaos injected and the run was INVALID. When editing a validated trigger, re-read the exact current range around the edit, verify no variable assignments were consumed (grep for each referenced variable's definition), and prefer a runtime smoke of variable resolution over syntax-only checks before resync. Evidence: `cbt-chaos/scenarios_v2/CBT-F-02/runs/20261010-f02-k7q4/` (invalid run, `/tmp` trigger console showing the unbound-variable abort) and the fixed rerun `cbt-chaos/scenarios_v2/CBT-F-02/runs/20261010-f02-m3r8/`.

- **2026-10-10 — Windows guest iteration needs no trigger changes:** A CBT-F-02 Windows Server 2022 iteration ran with `VM_OS=windows` and the same event-driven virsh trigger: the libvirt domain, `compute` container, and SIGTERM mechanism are guest-OS-independent, the same-VM recovery stage resolves the OS profile from run metadata (`os_profile` in vm-info), and the NTFS restore helper is selected from the remote `.env`'s `RESTORE_HELPER_IMAGE`. Prerequisites to verify before launch: cached Windows golden-image DataSource (`windows-server-2022`, `dv/windows-golden` Succeeded) and a readable `WINDOWS_ADMIN_PASSWORD_FILE`; OOBE adds ~5–10 min to setup and ~5 s to launcher-pod replacement readiness. Evidence: `cbt-chaos/scenarios_v2/CBT-F-02/runs/20261010-f02-w9t2/trigger.log`, `statuses.json`, and `observer/` (PASS, criteria identical to the RHEL 9 run `20261010-f02-m3r8`).
- **2026-10-11 — scenario trigger sizing defaults differ from framework defaults:** The CBT-F-04 trigger defaults its guest workload to 1 GiB files (window widening), while the framework/workflow default is 4–12 MiB and 8/4 files; a user request for "default file size and count" therefore requires explicitly setting `GUEST_BASE_FILE_COUNT`, `GUEST_INCREMENTAL_FILE_COUNT`, `GUEST_FILE_SIZE_MIN_MIB`, and `GUEST_FILE_SIZE_MAX_MIB` in the trigger's environment (env-prefix works because the trigger forwards them as make arguments). Compare each scenario trigger's default sizing against the requested workload before launch and confirm the printed pipeline configuration. Evidence: `cbt-chaos/scenarios_v2/CBT-F-04/chaos-trigger.sh` lines 12-16 vs `scripts/common.sh` lines 43-55, applied in `cbt-chaos/scenarios_v2/CBT-F-04/runs/win-f04-20261011-r01/trigger.log`.
- **2026-10-11 — remote trigger invocation must export dotenv values:** Running a scenario trigger over SSH after `source scripts/dotenv.sh && load_dotenv_defaults ./.env` fails immediately at the trigger's `: "${KUBECONFIG_PATH:?}"` guard because `load_dotenv_defaults` assigns without exporting; the first F05 launch exited before any resource was created. Export the needed variables for the child (`export KUBECONFIG_PATH GUEST_KEY`) in the remote invocation, and prefer the guard failing fast over pre-exporting whole `.env`. Evidence: `cbt-chaos/scenarios_v2/CBT-F-05/runs/20261011064508-fuzzy-wolf-6cb9/trigger.log` (successful relaunch) and `scripts/dotenv.sh` lines 15-18.
- **2026-10-11 — Windows first-boot QGA stall delays injection, not validity:** In a CBT-F-05 Windows run, the run-scoped clone's first guest-exec (startup workload verification) polled the QEMU guest agent for the full 900-attempt budget (~30 min) before the command completed; the run then proceeded normally. Windows clone boots can exceed any reasonable default `GUEST_EXEC_POLL_ATTEMPTS` (default 150 ≈ 5 min), so pass `GUEST_EXEC_POLL_ATTEMPTS=900` (or higher) in the trigger environment for Windows runs and treat a long pre-backup stall as a delay, not a failed injection window — the copy signal remains the valid injection gate. Evidence: `cbt-chaos/scenarios_v2/CBT-F-05/runs/20261011-win-f05-r01/observer/timeline.md` (13:06:04Z–13:39:04Z stall) and `runs/20261011-win-f05-r01/logs/workflow.log`.
- **2026-10-12 — `krknctl` native `--trigger-k8s-condition` pitfalls (unquoted literals; WaitForFirstConsumer bind is sub-second):** Two CBT-F-06 attempts failed to inject before a third succeeded. First, a condition watching a `WaitForFirstConsumer` destination PVC for `status.phase == Pending` never fired: on `cbt-demo-hpp`, `ADDED(Pending)` through `MODIFIED(Bound)` landed inside the same one-second API timestamp, faster than any poll interval (even krknctl already running before the PVC existed never caught it) — a PVC-phase-pending condition on this storage class is not an externally-observable window at all. Second, after switching to watching the owning `VirtualMachineBackup` CR's mere existence instead, the condition `metadata.name == 'vm-backup-<run-id>'` (single-quoted) never satisfied even though the object existed continuously for minutes; `krknctl`'s condition grammar compares against the field's raw unquoted value (its own documented example is `status.phase == Running`, no quotes), so the quote characters became part of a literal that could never match. Removing the quotes (`metadata.name == vm-backup-<run-id>`) satisfied on the very next 2s poll and the deletion landed correctly. When using any `--trigger-k8s-condition`: (a) never wrap the right-hand side in quotes, and (b) do not target a `WaitForFirstConsumer` PVC's `Pending` phase as a trigger condition — watch the owning request/CR's creation instead, and expect the destination PVC to already be `Bound` by the time any external trigger (krknctl or otherwise) can react, so frame "before the destination is bound" scenarios as "as early as the backup request can be observed," not literally pre-bind. Evidence: `cbt-chaos/scenarios_v2/CBT-F-06/runs/20261012-cbtf06-r01/observer/pvc.watch.jsonl` (Pending→Bound same second), `cbt-chaos/scenarios_v2/CBT-F-06/runs/20261012-cbtf06-r02/krknctl.log` (never satisfied with quotes), and `runs/20261012-cbtf06-r03/krknctl.log` (satisfied immediately once unquoted).
- **2026-10-12 — remote backgrounded observer watches: don't trust the `ssh` call's own return:** In CBT-F-06 run `20261012-cbtf06-r04`, starting each watch with `ssh <host> "... & disown"` sometimes left the local `ssh` client hanging well after the remote watcher process had already launched and written its ready-file (remote-side `nohup`/`disown` detached correctly; the hang was in the local SSH session's own return, likely stdin-related). Treat the local `ssh` invocation used to *launch* a backgrounded remote watch as fire-and-forget: don't block analysis on it returning — instead verify arming via a separate, fresh `ssh` command checking the ready-file and `kill -0 <pid>` on the remote host, and be prepared to kill stray local `ssh` client processes once remote arming is independently confirmed (killing the local client does not affect an already-`disown`ed remote process). This also validated end-to-end, on a fourth CBT-F-06 attempt, that the unquoted `VirtualMachineBackup`-existence `--trigger-k8s-condition` design from the prior dated entry above correctly lands the CSI-pod disruption inside the backup's active window and recovers cleanly. Evidence: `cbt-chaos/scenarios_v2/CBT-F-06/runs/20261012-cbtf06-r04/observer/` (ready-files + live PIDs confirmed independently by the parent before/at injection) and `runs/20261012-cbtf06-r04/test-run-report.md` (PASS).
- **2026-10-13 — `krknctl --trigger-command` conditions must be shell-validated before a run:** Krkn's command trigger executes its string via `subprocess.run(cmd, shell=True)` and logs ONLY on state change, so a condition that can never evaluate true (unquoted JSONPath parentheses `?(@.type==…)` inside `$(…)` are a shell syntax error; nested double quotes break the same way) is indistinguishable in the tool's log from "not yet satisfied" — CBT-F-08 burned two full attempts (r02, r05) on this before reproduction proved it. Before any run using a command trigger: expand the exact `printf -v` result and execute it via `bash -c` against live terminal-state objects, confirming each clause evaluates (rc from the real state, not a parse error). Single-quote the JSONPath inside the command substitution. Evidence: `cbt-chaos/scenarios_v2/CBT-F-08/runs/20261012-cbtf08-r06/krknctl.log` (working form) vs `runs/20261012-cbtf08-r05-invalid-trigger-quoting/krknctl.log` (broken form, single "not satisfied" line).
- **2026-10-13 — PVC-fill chaos must be sized to the real disk geometry and validated against a live PVC:** The Debian+ODF guest root disk is 4.98 GiB virtual (manifest hardcodes a 5 Gi request regardless of the 6 Gi PVC), minus Debian OS and ext4 reserved blocks ≈ 3.5 GiB safe payload; 4.5 GiB workloads ENOSPC'd twice during baseline init (CBT-F-08 r03/r04). Also validate the fill mechanism itself before a live run: krkn's pvc-scenarios picks a random pod from the PVC's `podNames`, `df`s the mount path, and fallocates `kraken.tmp` to the target percentage — a completed backup's PVC has no attached pod (fill fails "Pod … not found"), and a `Block`-mode PVC would break `df`. Empirical pre-validation against a sacrificial pod attached to a real completed-backup PVC proved the whole path (df parse, fallocate as non-root qemu user, hold, clean removal). Evidence: `cbt-chaos/scenarios_v2/CBT-F-08/runs/20261012-cbtf08-r06/` (valid run) and the archived `-invalid-oversized-workload` attempts.
- **2026-10-13 — expect krkn PVC-fill cleanup to fail when the backup itself fails:** When the injected fill makes the backup fail, KubeVirt's failure cleanup unplugs the destination PVC and deletes the hotplug attachment pod — while krkn is still inside its `--duration` sleep. Its post-sleep `rm` then errors ("impossible to determine the shell") and krknctl exits 1 even though the injection fully succeeded. Treat that exit as expected for failure-expected scenarios: the trigger propagating krkn's status will skip its own recovery stage, so run `make e2e TYPE=recover` manually, and document the leftover `kraken.tmp` on the failed backup's PVC (harmless; that PVC is never restored). Evidence: `cbt-chaos/scenarios_v2/CBT-F-08/runs/20261012-cbtf08-r06/krknctl.log` (00:01:44 cleanup error) and `trigger.log`.
- **2026-10-13 — krkn's node-cpu-hog/node-memory-hog are broken in this krkn version (readOnlyRootFilesystem):** the hog pod template (`krkn-lib` `hog_pod.j2` via `deploy_hog`) sets `readOnlyRootFilesystem: true`, but the hog image's `/stress-ng/run.sh` writes its stress-ng jobfile (`hog-jobfile.conf` and `output.yaml`) to the container CWD — only the **io** branch `cd`s into a hostPath-mounted `STRESS_PATH`. cpu/memory hog pods therefore die in ~1 s with `hog-jobfile.conf: Read-only file system` and apply zero pressure, while io-hog works. CBT-F-10 r01 burned a full lifecycle on this (backup "passed" with no chaos applied — only the observer's hog-pod watch caught the instant exit). Before any cpu/memory hog run on this stack: either pre-validate the pod actually runs its full duration, or use the documented direct-injection fallback — `kubectl run` the same pinned hog image with `cp /stress-ng/*.template /stress-ng/run.sh /dev/shm/ && cd /dev/shm && HOG_TYPE=cpu WORKERS=N LOAD_PERCENTAGE=P DURATION=D ./run.sh` (tmpfs stays writable under readOnlyRootFilesystem; live-validated, measured cpu-usage-per-instance ≈ LOAD_PERCENTAGE). Always treat "backup succeeded during chaos window" as unproven until the hog pod's own Running duration and exit code are verified. Evidence: `cbt-chaos/scenarios_v2/CBT-F-10/runs/20261013-cbtf10-r01-invalid-hog-readonly-fs/observer/hog-pods-poll.jsonl` (cpu-hog-cyvry exit 1 at 01:01:40Z) and the hog-verify-f10 validation run.
- **2026-10-13 — verify a trigger window is non-empty against a raw watch stream BEFORE building a condition on it:** CBT-F-11 r01's condition "`Progressing=True` AND `virsh backup-dumpxml` fails" was never satisfiable — the observer's vmbackup watch proved `Progressing` flips to True at the same instant the libvirt copy starts (creation 01:32:32Z → Progressing+copy 01:32:34Z → Done 01:33:26Z), and the true pre-copy phase (`Initializing`) lasts ~2 s, shorter than krkn's helper-pod deploy latency. The krkn runner silently waited the entire run (a single "trigger condition not satisfied" line; no filter, no helper pod) while the backup completed cleanly — a trap that yields a false PASS if injection validity isn't independently verified. Two reusable rules: (1) when a Jira asks for a sub-phase window, first capture the backup's full condition timeline from a raw watch (or a prior run's observer JSONL) and measure the window's actual length against the chaos tool's deployment latency (~5–15 s for krkn's helper pods); if shorter, fire at a superset boundary (e.g. object existence pre-Done) and document that the filter lands inside the intended window; (2) also note krkn's pod-network-filter mechanism for future scenarios: it deploys a privileged hostPID helper pod (pod-filter-*) on the target's node in the SCENARIO namespace, resolves target container PIDs via /proc cgroup scan, and `nsenter --net -- iptables -I/-D` inside the target's netns — no NetworkPolicy objects are created, so verify injection by the helper pod + krknctl.log iptables lines, not `oc get networkpolicy`. Evidence: `cbt-chaos/scenarios_v2/CBT-F-11/runs/20261013-cbtf11-r01-invalid-empty-window/observer/` (condition timeline) and krknctl.log (single not-satisfied line).
- **2026-10-13 — "Done != True" on a MISSING object is vacuously true — always gate on object existence first:** CBT-F-11 r02's condition (backup pre-Done AND launcher exists) fired 68 s before the backup object was created: `oc get vmbackup <name>` on an absent object prints nothing (rc 0 with 2>/dev/null), so `test "$(...)" != True` passes. The launcher pod existed but was still Pending/unassigned, so krkn resolved the target's `nodeName` as None and rendered its helper pod with `nodeSelector kubernetes.io/hostname=None` — FailedScheduling on all 31 nodes, 300 s pod-wait timeout, "Pod creation failed Starting pod failed", krknctl exit 1, zero chaos applied. Reusable rules: (1) every compound condition on a not-yet-created object needs an explicit existence probe (`oc get <kind> <name> --ignore-not-found -o jsonpath='{.metadata.name}'` non-empty, or check rc of plain `oc get`); (2) when the chaos target's placement derives from a pod's `spec.nodeName`, require that field non-empty in the condition — a Pending pod poisons downstream node selectors with literal None; (3) validate a new condition against BOTH edge cases (nothing exists yet, and a terminal-state object from a prior run) before launching, expecting rc=1 from both. Evidence: `cbt-chaos/scenarios_v2/CBT-F-11/runs/20261013-cbtf11-r02-invalid-helper-unschedulable/observer/` (launcher node=None transitions, helper FailedScheduling events) and krknctl.log (creation at 01:48:07.591Z vs backup creation 01:49:16Z).
- **2026-10-13 — krknctl vs plugin schema mismatches: four distinct failure modes, one scenario (CBT-F-12):** a single `krknctl run pod-network-filter` invocation burned four full lifecycles before a valid injection: (r01) boolean flags `--ingress`/`--egress` have NO defaults — omitting one fails config validation before any cluster action; (r02) `--namespace` is the TARGET pod's namespace (krkn looks up the target AND deploys its helper there), not a "scenario container namespace"; (r03) `--pod-name` does NOT populate the plugin's `target` field — `get_pod_targets()` reads `config.target`/`label_selector` only, and the CLI exposes no flag that maps to it, so every run aborts `neither node selector nor node_name (target) specified` while `--dry-run` passes ✔✔✔; (r04) the workaround (upstream krkn via official container image) needs the mounted kubeconfig readable by container uid 1001 (chmod 644). Consolidated in `cbt-chaos/krknctl-bugs.md`. Rules: treat `--dry-run` as necessary-not-sufficient; grep the live runner log for the abort strings immediately after the watcher returns; when the CLI cannot express the plugin config, run upstream krkn directly (`run_kraken.py` under `python3.11`, list-of-configs scenario YAML with `target:`/`taints:` set, all top-level kraken-config sections required).
- **2026-10-13 — krkn rule leak on target restart mid-chaos (CBT-F-12 r05):** a 60 s egress block on the virt-controller leader tripped the pod's liveness probe; the container restarted mid-chaos, and krkn's cleanup nsenters the container PIDs captured at apply time (now dead) — the iptables rule SURVIVED chaos end in the (persisting) pod netns while krkn exited 0 and reported success. The target crash-looped until pod deletion (fresh netns). Any network-filter scenario must include a post-chaos target-connectivity check (curl the API VIP from inside the pod) and treat "krkn exit 0" as insufficient proof of cleanup. The F-12 trigger implements this as the RULE-LEAK GUARD (verify + delete + log).
- **2026-10-13 — controller-plane chaos needs controller-pod AND lease telemetry, not just workload watches:** the decisive F-12 evidence was a 5 s lease poll (`holderIdentity`+`renewTime`: m5zkb renewals stop 03:49:14.6Z, standby acquires 03:49:35.8Z → ~21 s gap ≥ 15 s leaseDuration) plus a controller-pods poll (restartCount/ready per replica). Two practical notes: the correct label selector is `kubevirt.io=virt-controller` (`kubevirt.io=name=virt-controller` is an invalid selector returning empty lists silently), and remote poll scripts must be scp'd + chmod +x + `nohup setsid` (plain nohup over ssh dies with the session; inline-ssh quoting mangles timestamps). Record format `TS\t[{name,restartCount,ready}]` per line.
- **2026-10-13 — sub-second phase windows must be gated by superset + post-hoc event proof (CBT-F-13):** the Jira's "copy completed but final status not yet recorded" window is literally sub-second on this stack — Done flip, VolumeUnMountedFromPod, and hp-volume attachment-pod deletion all land in the same second (measured from F-12 r05 events) — so no poll-based condition can gate on it. Working pattern: gate on the observable superset (backup exists ∧ Done≠True ∧ attachment pod present, 1 s cadence in the trigger itself, existence probe first), let the kill land in the copy phase, and prove post-hoc from the events timeline that the disrupted reconcile spanned copy completion → cleanup → checkpoint write (deletion timestamp vs Done/unmount/attachment-delete timestamps). Result: takeover replica completed cleanup exactly once, no orphaned attachment, no stale VolumeAttachment, single checkpoint — first-attempt PASS. Also: `oc delete pod <leader> --grace-period=0 --force` is the sanctioned direct equivalent of a krkn pod-scenario when the target must be resolved from a lease at condition time (krknctl cannot express it).
