## Highlights

### The 2 FAILs

- **CBT-F-05 (handler kill during full copy) — product defect:** virt-handler killed mid-68s-copy; the unplug raced with handler replacement — replacement logged EBUSY removing the hotplug dir (vm.go:1493), marked the volume unmounted anyway, and leaked: VolumeAttachment never deleted (external-attacher finalizer), `/dev/rbd7` stale-mounted inside the replacement handler's hotplug-disks path, Ceph watcher held, `rbd unmap` EBUSY for 238 retries over 2h+. Restore-verify pod stuck Pending 53min on Multi-Attach → lifecycle FAIL 34m48s. Data itself was intact (17/17 after cleanup); workaround (delete orphaned VA + restart handler) verified. Bug draft: `CBT-F-05/bugs/leaked-hotplug-attachment-on-handler-restart.md`.
- **CBT-I-02 (launcher kill during incremental copy) — tracker-clearing semantic + workflow defect:** launcher killed 4s into p01's Progressing window. The incremental failed cleanly (`VMI was deleted during backup`, no corruption), but 9s later the tracker emitted `CheckpointRedefinitionFailed … Checkpoint cleared, next backup will be full` → `.status={}` — the incremental chain is severed (design intent, correctly surfaced). The workflow then offers NO sanctioned retry after a failed incremental: `TYPE=incremental` needs `incremental_ready`, `TYPE=recover` only admits a failed FULL, `TYPE=verify` needs a completed pass plan, `TYPE=extend` needs complete — the Jira's "incremental operation can be retried" is unreachable. Restore verification structurally impossible in that state (part of the finding). I-05 later isolated the tracker clearing to the VMI-death path (with VMI alive, a failed incremental does NOT clear the tracker).

### The X-03 incident (node down, backup survived)

Direct-krkn `pod_network_filter` with `ports: []` on the run's launcher pod escalated into a TOTAL node TCP outage on d38-h18-000-r660: krkn resolved 8 pids including host-side container helpers and applied all-ports DROP in the host netns; its cleanup then failed, leaving a permanent leak. Node NotReady since 17:22:49Z (2026-10-13), pending manual reboot (BMH unmanaged). The full backup nonetheless completed Done=True DURING the block — the strongest possible evidence that CBT data movement is node-local and network-independent. Node-down side effect is a krkn defect (bug #11), not a CBT failure.

### Strongest resilience findings

- **X-01:** 40% node-memory pressure (49GiB max-rss, whole copy covered) — zero slowdown, zero OOM, bit-exact restore.
- **X-02:** kubelet restart mid-copy — control-plane-only for CBT; same launcher pod, restartCount=0, 54s full, node never NotReady.
- **R-03:** storage-plugin eviction (NoExecute taint) → verifier waits cleanly at scheduling (Pending, never crash-loops) and starts within seconds of the plugin returning.
- **F-04 / F-03 / F-13 / I-03:** virt-controller leader kills at start, mid-copy, cleanup, and pre-tracker-write — copy continues or fails over cleanly; tracker updates exactly once in every case (I-03's watch-rV proof: kill < tracker write < Done flip).
- **F-07:** CSI plugin restart mid-copy — already-mounted dest unaffected, 55s vs ~52s baseline.
- **I-04 / R-02 (paired):** I/O contention is device-relative — foreign-device hogs (even O_DSYNC) don't slow the incremental; same-device dsync hogs slow restore verify ~19% with zero correctness impact.
- **F-11:** 22-port tcp/udp DROP in the launcher's pod-netns — zero impact on the backup (data path node-local).
- **I-08 vs I-02 (comparison):** container-kill mid-copy → tracker HOLDS previous checkpoint; full launcher-pod deletion → tracker CLEARED. Both recover via fresh-launcher checkpoint redefinition.

## krkn / krknctl defects found during the campaign (11)

Full detail: `cbt-chaos/krknctl-bugs.md`.

1. **cpu/memory-hog workload image crashes on readOnlyRootFilesystem** — hog jobfile written to read-only root fs; workaround: direct pod copying workload to `/dev/shm` (F-10) or emptyDir (X-01).
2. **Boolean flags have no defaults** — `pod-network-filter` requires BOTH `--ingress` and `--egress` explicitly or config validation fails pre-action.
3. **`--namespace` is the TARGET pod's namespace**, not a workload namespace — CLI help text is misleading (F-12 r02).
4. **`--pod-name` does not populate the plugin's `target` field** → "neither node selector nor node_name (target) specified, aborting"; source-verified schema disagreement between CLI and network_chaos_ng plugin.
5. **`--dry-run` does not validate target resolution** — passes ✔✔✔ for invocations the live run rejects in <1s; necessary-not-sufficient.
6. **(Validated workaround recipe)** run upstream krkn directly via `podman run quay.io/krkn-chaos/krkn:latest` + `python3.11 run_kraken.py` with a hand-written scenario YAML where `target:` is set directly.
7. **RULE LEAK:** iptables filter survives chaos end when the target container restarts mid-chaos (cleanup nsenters dead PIDs) — silent permanent pod isolation while krkn reports success; recovery = pod deletion.
8. **Semantic: container-scenarios `--action N` sends SIGTERM to PID N**, not signal N — `--action 9` is a silent NO-OP; `--action 1` is the real "stop container".
9. **node-memory-hog does not create its target namespace** → pod-creation 404; pre-create the namespace.
10. **krkn-hub hog image writes its jobfile to a read-only WORKDIR** → instant exit 1 in-cluster for krkn-scheduled pods; workaround: direct pod with `cp -r /stress-ng/. /work/` + emptyDir.
11. **`pod_network_filter` with `ports: []` is NODE-DESTRUCTIVE** — all-ports DROP lands in the host netns (8 pids resolved incl. host helpers) and failed cleanup makes it permanent → node outage until reboot (the X-03 incident). Never run without out-of-band node access; prefer explicit port lists.
