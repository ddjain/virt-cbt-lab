## What this is, in one paragraph

Changed-block tracking (CBT) backups use a checkpoint (the metadata naming the disks a backup covers) and a dirty bitmap per disk (the per-disk change-tracking map inside the running VM's QEMU). Two independently graded CBT-EXP-06 attempts with a proven valid injection showed that after one disk's full-checkpoint bitmap is removed and the VM instance restarts once, the next incremental backup *wedges*: it stays in its creation-time Initializing state with its finalizer held, while QEMU refuses the backup start citing the missing bitmap. Neither attempt could determine the wedge's **terminal disposition** — whether the backup eventually fails terminally, clears its checkpoint, falls back to a full backup, or holds its finalizer forever — because both approved observation windows (20 minutes, then a 75-minute two-phase window) were exhausted while the wedge persisted. This ticket proposes the follow-up experiment whose single primary question is exactly that disposition, observed for longer (a read-only leg) or probed by a product-side intervention.

**When → then → expected**

- **When** a fresh two-disk surgery VM has a successful full backup covering both disks (rootdisk and datadisk), and the verified CBT-EXP-06 composite fault — QEMU `block-dirty-bitmap-remove` of exactly the datadisk full-checkpoint bitmap plus one UID-preconditioned VMI restart — is applied inside the full-Done-to-incremental-creation window, and the next incremental backup is created (the same reproduction mechanism proven valid twice; **not a krkn fault**: krkn's installed scenarios cannot perform a per-disk QEMU bitmap mutation).
- **And** the disruption **CBT-EXP-11** observes the resulting wedge beyond the already-exhausted 75-minute bound: either **Option A** — a bounded read-only observation leg of at least 4 hours on a freshly reproduced wedge — or **Option B** — an approved product-side intervention leg (for example a controller reconcile trigger, a VMI restart, or a second-backup probe on the same VM) applied to a freshly reproduced wedge. The option, sizing and any intervention are for human review to choose; no executable bundle exists.
- **Then (current behaviour, from the closed evidence):** the wedged incremental stays `Initializing=True` / `Progressing=False` with its creation-time reason, holds the `backup.kubevirt.io/vmbackup-protection` finalizer, sets no type/Done/includedVolumes, and its `resourceVersion` freezes; the failure surfaces only on the VMI (Warning BackupError events quoting QEMU `virError Code=109` "checkpoint inconsistent: missing or broken bitmap … for disk vdb") while the backup CR's own event stream stays empty. This was observed at the 20-minute bound (iteration 3), through the full 75-minute two-phase window plus the 300s collector window (iteration 4, resourceVersion frozen at 29911561 across all 111 wedge samples, backup age ~4801s at final collection), and in a post-close read-only baseline at ~3.5h after creation (iteration-3 wedge still nonterminal, VMI BackupError count still climbing 21→31, last at 08:43:34Z).
- **Expected behaviour:** the wedge reaches a terminal disposition within the approved window — a terminal failure condition with finalizer release and destination-volume detach, a checkpoint clearing, or a full-backup fallback — **or** it is still nonterminal at the approved bound, which is recorded as stronger recurrence evidence for the archived livelock ticket family and still not proof of a permanent hang. Which of these the product does is exactly what this scenario measures.

## Context (for an engineer new to this area)

- **What the feature does** — KubeVirt CBT push-mode backups. A `VirtualMachineBackup` CR copies a VM's disks into a destination PVC hot-plugged only while the copy runs. Incremental passes work from a chain: a checkpoint per backup, a dirty bitmap per disk inside the running QEMU, and a `VirtualMachineBackupTracker` CR holding the chain's latest checkpoint. On VM-instance restart, checkpoint redefinition rebuilds the checkpoint from the disks that still have a bitmap.
- **Where the failure sits (observed)** — the incremental backup CR never leaves its creation-time `Initializing=True` / `Progressing=False` conditions, never sets type/Done/includedVolumes, and holds `backup.kubevirt.io/vmbackup-protection`. Its destination PVC stays attached (VolumeAttachment, node pin, host device, attachment pod). The libvirt checkpoint is redefined to vda-only while the tracker and the VMI backupStatus still name both volumes, and the incremental checkpoint the VMI advertises does not exist in libvirt (`virsh checkpoint-dumpxml` → "Domain checkpoint not found").
- **Observed surface vs. origin** — the failing object is the backup CR, but every failure signal lands on the VMI (Warning BackupError) and the virt-controller log; the backup CR's own event stream is empty in both iterations. An operator reading only the backup object sees a pass "still attaching its volume" indefinitely. Whether that mismatch persists over a longer window is part of what the observation leg measures.
- **Why it matters** — a backup that never terminates holds its finalizer and destination attachment and (per the archived lead, not the closed runs) may block the VM's one-backup-per-source guard. Until the disposition is known, the correct product classification (bounded-but-slow failure vs permanent livelock) — and therefore the correct fix — cannot be chosen.

## Impact, workaround and data safety

- **If the wedge is eventually terminal (bounded failure):** impact is a delayed, noisy failure — backup coverage lost for the affected VM until the pass terminalizes, with failure signals visible only on the VMI.
- **If the wedge is permanent (never terminal):** impact is loss of backup coverage for the affected VM, a held finalizer, and a retained destination-volume attachment (VolumeAttachment, node pin, host device, attachment pod — as observed in both closed runs) until an operator intervenes. Not cluster-wide; other VMs are outside the fault scope.
- **Data safety:** no data-corruption risk is modelled — QEMU's checkpoint-consistency check refuses the inconsistent backup (the closed runs never saw a copy start). The harm is backup *coverage* and stuck resources, not guest data; the guests stayed Running/Ready with readable workload files throughout every closed observation.
- **Workaround:** none is claimed here. The archived lead ticket documents operator actions from its own (different) runs — deleting the wedged CR with the tracker present, or a `forceFullBackup` — but this proposal neither asserts nor authorizes any workaround; any intervention leg needs its own approval (Step 3, Option B).
- **Frequency:** not claimed. Two closed valid-injection iterations reproduced the wedge shape; no production frequency or affected-version claim is made.
