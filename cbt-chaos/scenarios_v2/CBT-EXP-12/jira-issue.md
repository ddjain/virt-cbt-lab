**Purpose:** Determine whether deleting the `virt-controller` leader pod *inside* the sub-second window between the VMI's backup-status cleanup and the backup CR's terminal `Done=True` write can flip a completed backup's terminal condition (the stale-reconcile race hypothesized in EXP-03), by triggering the kill on the **VMI-side cleanup signal** rather than the CR-side Progressing flip that EXP-03 proved fires only after the race is already closed. ## What this is, in one paragraph

A changed-block-tracking (CBT) full backup (a `VirtualMachineBackup` CR copying a VM's disks into a temporarily hot-plugged destination volume) finishes in two back-to-back API steps: the virt-controller first clears the backup status stored on the VM instance (`VMI.status.changedBlockTracking.backupStatus` — the "VMI-state cleanup"), then writes the backup CR's terminal `Done=True` / `Progressing=False` conditions. Source analysis suggests a controller crash between those two writes could let a stale reconcile overwrite the just-completed terminal state (or emit a spurious `SourceLost`). The EXP-03 attempt (3 jittered leader kills at boundary +0/+1/+2 s) graded PASS with **race-window-not-entered**: its trigger watched the CR's `Progressing` flip at a 1-second poll, and the closed-run evidence shows the cleanup write and the terminal write are ~2 resourceVersions apart inside the same second — the flip **is** the Done write, so the poll can never fire inside the gap. This experiment proposes the follow-up whose single primary question is what happens when the kill actually lands inside that sub-second gap, using a VMI-watch trigger on `backupStatus` removal. It is **not a krknctl scenario**: no installed krkn scenario can watch a VMI status subfield and fire a sub-second-conditioned pod deletion; the trigger must be custom harness machinery (see Unknown prerequisites).

**When → then → expected**

- **When** a fresh virtual machine's full push-mode `VirtualMachineBackup` is in its final teardown — destination volume detached, VMI hotplug volume removed — and the VMI's `status.changedBlockTracking.backupStatus` for that backup is removed from the VMI object while the backup CR has **not yet** written its terminal `Done=True` condition.
- **And** the disruption **CBT-EXP-12** is applied: `oc delete pod <leader> -n openshift-cnv --wait=false`, where `<leader>` is resolved live from the `virt-controller` Lease at action time — the same proven action shape as EXP-03, but fired by a VMI-watch trigger on the cleanup write rather than a CR poll on the terminal write.
- **Then (current behaviour — unknown, this is the experiment):** no run has entered the gap. The closest evidence (EXP-03 iteration 1) shows leader kills landing **after** the first `Done=True` observation produce no condition flip, no `SourceLost`, and intact incremental chains and restores; a same-second event-only `VirtualMachineBackupFailed: "Backup has failed: VMI backup status was lost"` warning also occurred with no injection active at that instant.
- **Expected behaviour (hypothesis under test):** either the completed backup's terminal condition is overwritten after its first observation, or a persistent `SourceLost`-after-`Done` appears (both reportable defects per the EXP-03 contract), or the product proves resilient at n legs with the gap genuinely entered (event-only transients recorded as the known cross-run misleading signal).

## Context (for an engineer new to this area)

- **What the feature does** — KubeVirt CBT push-mode backups. A `VirtualMachineBackup` CR copies a VM's disks into a destination PVC hot-plugged only while the copy runs. While a backup is active, the VM instance object (`VMI`) carries a `status.changedBlockTracking.backupStatus` stanza naming the in-flight backup and checkpoint. Completion is a two-step status write: the controller clears that VMI stanza (cleanup), then writes the backup CR's terminal conditions (`Progressing=False`, `Done=True`, reason `Successfully completed VirtualMachineBackup`).
- **Where the hypothesized failure sits** — between those two writes. If the leader controller dies in that gap and a surviving/replacement worker later reconciles from a stale informer cache, the full-object `UpdateStatus` could overwrite the just-written terminal condition or persist a `SourceLost`-style failure for an already-completed backup. No run has observed this; the hypothesis comes from source analysis plus the campaign-wide completion-instant `VMI backup status was lost` warning events (an event-only stale-reconcile signature).
- **Observed surface vs. origin** — the misleading warning event lands on the **backup CR** (`Warning VirtualMachineBackupFailed`) at the success instant while the terminal condition on the same object stays `Done=True`; in the wedge family (EXP-06/11) failure signals instead land on the VMI. Operators reading events see "failed"; operators reading conditions see "succeeded". Whether a kill inside the cleanup→Done gap upgrades that event-only mismatch to a condition flip is exactly the measurement.
- **Why it matters** — a completed backup whose terminal state is overwritten after first observation is a state-correctness defect: consumers that watch conditions (rather than events) would propagate a false terminal failure for a backup that actually completed, and the chain/restore correctness under such a raced completion is unmeasured.

## Steps to reproduce (exact commands and injection timing)

**These are APPROVED-BUT-UNEXECUTED command shapes for discussion, not evidence of a repro and not a runnable bundle.** No executable exists for CBT-EXP-12; any implementation requires a prepared bundle, Lead-owned approval binding complete file hashes and parameters, a fresh run root with run.json, and fresh lifecycle identities. The placeholder shapes below reference the proven EXP-03 mechanism; a real bundle would render its own run-scoped names.

**Step 1 — Arm the VMI-watch trigger before the backup starts.** On a dedicated cluster with new run-scoped names, start a namespaced field-scoped watch on the leg's VMI and the leg's backup CR before creating the full backup (the watch's own baseline capture must prove it is live pre-creation, exactly as EXP-03's observer baselines did):

```bash
oc get vmi <leg-vm> -n <ns> -w -o json | jq -c --unbuffered 'select(.status.changedBlockTracking.backupStatus == null and .status.changedBlockTracking.state == "Enabled") | {rv:.metadata.resourceVersion, cbt:.status.changedBlockTracking}'
```

**What you must see (shape, not values):** a stream that recorded `backupStatus` present during the backup (copy phase), then one object whose `backupStatus` is gone while `state` stays `Enabled` — the cleanup write. A watch that starts after the backup was created, or whose stderr shows a re-list/retry, is not valid trigger evidence.

**Step 2 — Fire the leader deletion on the cleanup write, with a fail-closed precondition.** When the trigger observes the cleanup write, immediately resolve the leader and delete it — the recorded action shape, unchanged from EXP-03:

```bash
leader=$(oc get lease virt-controller -n openshift-cnv -o jsonpath='{.spec.holderIdentity}')
oc get pod "$leader" -n openshift-cnv -o json > <leader-pre-delete-snapshot>   # UID captured before the delete
timeout -k 5 60 oc --request-timeout=30s delete pod "$leader" -n openshift-cnv --wait=false
```

**What you must see (shape):** the pre-delete snapshot's UID equals the lease holderIdentity; delete rc=0; the independent controller-pods watch later shows that UID with a deletionTimestamp, phase Failed, a terminated container, a DELETED event, and a replacement pod. A bare exit 0 is not effect proof. The decisive timing measurement is whether the delete request (or the container's SIGTERM delivery) can land before the backup CR's terminal write — recorded per leg from the raw watch streams' resourceVersion order, honestly classified as entered / not-entered, never forced either way.

**Step 3 — Capture the full timeline.** Keep the backup-CR watch, VMI watch, backup-CR event watch, tracker watch and controller-pods watch running well past the terminal write (EXP-03's streams ran ~2 minutes past terminal), then capture final CRs, events, tracker and residual probes per leg, exactly as the originating attempt's evidence set did.

**Step 4 — Verify the chain.** Let the lifecycle's incremental pass and restore verification complete on the same VM (the existing deterministic checks: tracker/checkpoint distinctness, full and incremental-prefix restore hashes) — reused, not rerun, by the future grading owner.

**Step 5 — Preserve.** No recovery or cleanup mutation is authorized by this proposal. Recovery is automatic (the deployment recreates the replica; the standby takes the lease). Run-scoped backups/PVCs/trackers are preserved as evidence; only invocation-owned local watcher processes are stopped.

## Current behaviour (observed — closed-run evidence, not this proposal's run)

All facts below are independent artifact observations from the closed, independently graded CBT-EXP-03 attempt `18-10-2026-07-29-56-vm-exp03-boundary-kill-iteration-1` (verdict PASS, injection valid, 3 legs):

- **The two status writes are sub-second neighbours, and the EXP-03 trigger structurally cannot enter the gap.** Per leg, the VMI watch stream shows the leg's `backupStatus` last present at resourceVersion N and first absent at N+1 (leg1: 30769146 → 30769147; leg2: 30773555 → 30773556; leg3: 30778124 → 30778125), while the backup CR's terminal write — carrying `Progressing=False` **and** `Done=True` together — lands 2–3 resourceVersions later (leg1: 30769149; leg2: 30773558; leg3: 30778128), all within the same wall-clock second (07:32:55Z / 07:36:24Z / 07:40:04Z). The Progressing flip that EXP-03 polled at 1 s is therefore the same API write as `Done=True`: every kill fired after the race was closed (pre_done=true in all pre-action snapshots; offsets landed +0 s / +2 s (declared +1 s, rounding) / +2 s).
- **Post-Done leader kills are resilient 3/3.** Each leg's full backup has exactly one terminal write and zero subsequent CR writes (streams ran ~2 minutes past terminal; a read-only live API check hours later still showed the terminal resourceVersions with `Done=True`). No `SourceLost` anywhere in any observer stream. Incremental chains recorded exactly once per leg; full and incremental-prefix restore hashes passed with 0 failed checks on all three lifecycles. Standby replica untouched; deployment 2/2 ready; lease re-elected after every kill.
- **The misleading event-only signal occurs on this attempt's own backups, including with no injection active.** Leg 3's full backup emitted `Warning VirtualMachineBackupFailed: "Backup has failed: VMI backup status was lost"` (event rv 30778129, firstTimestamp 07:40:04Z) **after** the terminal CR write (rv 30778128) but **~2 s before** the leg-3 delete request (07:40:06Z) — spontaneous at the completion boundary. All three legs' incremental backups showed the same warning+success event pair at their success instants under the post-kill leader. No condition flip followed in any case. (Campaign-wide recurrence of this signature was already the EXP-03 spec's stated hypothesis source; recorded here as observation, root cause not determined.)
- **[Inference, labelled]** Because the cleanup write precedes the terminal write by ~2 resourceVersions within the same second, a trigger that reacts to the cleanup write has a sub-second head start over the EXP-03 trigger — but whether the delete request, the API-side grace period and the container's SIGTERM delivery can complete before the terminal write is **unknown**: it depends on request latency and the product's write cadence in the version under test, which no closed run measures.

## Expected behaviour (contract)

- **Primary criterion — gap genuinely entered:** per leg, the raw VMI/backup-CR watch streams must show the delete request (or container termination) ordered **between** the `backupStatus` removal and the terminal `Done=True` write by resourceVersion order. Legs where the kill lands after the first `Done=True` are honest timing outcomes, classified race-window-not-entered exactly as EXP-03's were — never counted as gap-entered legs and never treated as harness failures.
- **Primary measurement (gap-entered legs):** whether any failure condition or event appears **after** the first `Done=True` observation — a condition flip (terminal state overwritten: Done/reason changes after first observation, or persistent `SourceLost`-after-`Done`) is a reportable defect; an event-only transient is the known misleading signal. Plus the EXP-03 secondary criteria on gap-entered legs: final Done reason, incremental chain integrity (tracker checkpoints exactly once), restore hashes.
- **Verdict mapping (for the future grading owner):** valid injection + condition flip or persistent SourceLost on a gap-entered leg = FAIL (bug filed with the valid-injection proof); valid injection + all gap-entered legs resilient = PASS at the achieved n; no leg enters the gap after honest attempts = the timing result itself, reported explicitly (INCONCLUSIVE for the race question, with the trigger-latency evidence recorded). A failed/interrupted backup is not automatically a violation — the contract is about the completed backup's terminal state.
- **Validity gates:** the trigger's watch must be proven live before backup creation (baseline + stderr); the leader must be the current lease holder at action time (UID-verified); effect must be proven from the independent controller-pods stream, not from the delete's exit code; excluded resources (standby replica, campaign VMs, prior-run preserved objects) must be shown untouched. Missing evidence is UNKNOWN, never a silent PASS.

## Impact, workaround and data safety

- **If the race is real (condition flip):** a completed backup's terminal success state is falsified after first observation — monitoring/GitOps consumers watching conditions propagate a false failure; the chain/restore correctness under the raced completion is the adjacent measurement. Blast radius per event: the one run-scoped backup CR; the fault itself is a transient leader deletion (seconds) affecting the shared controller deployment with automatic standby takeover.
- **If the product is resilient at gap-entered n:** the EXP-03 conclusion is strengthened from "resilient after Done" to "resilient inside the completion gap", and the campaign-wide completion-instant warning event is confirmed event-only at the tightest achievable timing.
- **Data safety:** no guest-data corruption path is modelled — the fault is a control-plane pod deletion with a 2-replica deployment and automatic lease takeover; the originating run's guests stayed Running throughout with intact restore hashes. The dimensions at risk are terminal-state truthfulness and chain correctness, not guest data.
- **Workaround:** none claimed. If a flip were observed, the product fix belongs to the controller's status-write path (e.g., not writing terminal conditions from a stale cache copy); this proposal does not propose an unverified product fix.
- **Frequency:** not claimed. No run has entered the gap; the natural-occurrence probability of a leader crash inside a sub-second window is unknown and irrelevant to the contract question (the experiment forces the timing).

- **Can a VMI-watch trigger react fast enough?** The cleanup→Done gap is ~2 resourceVersions within one second. Options for human review: (a) pre-resolve the leader before the backup's copy phase ends and watch only for the cleanup write (removes the lease lookup from the critical path, at the cost of a staleness precondition on the holder identity); (b) pre-stage the delete as a shell command fed by a FIFO so only the trigger-to-exec hop remains; (c) accept post-terminal landings and measure the achieved distribution honestly.
- **Can krkn express this?** No: krkn's installed scenarios have no VMI-status-subfield watch trigger and no sub-second conditioned pod deletion; this requires custom harness machinery (as EXP-03 already used for its boundary watcher — the same pattern with a different signal source). - **Timing machinery needed:** a sub-second-resolution action timestamp (the EXP-03 run's second-granularity UTC stamps were honest but coarse — resourceVersion order carried the proof); an explicit definition of "entered" (delete request received by the API before the terminal write's resourceVersion, or container SIGTERM delivered before it — human review must pick one and record it in the spec before approval); and a fail-closed precondition that the backup CR is not already Done at fire time (the EXP-03 pre-action snapshot pattern, tightened to the trigger's own read).
