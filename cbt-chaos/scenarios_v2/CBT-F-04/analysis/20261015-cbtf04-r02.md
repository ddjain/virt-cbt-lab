## 3. Product findings (CBT behavior)

**P1 — HotplugFailed events during post-backup volume detach (non-blocking anomaly).**
Two distinct Kubernetes Event objects with reason `HotplugFailed` were emitted by `virt-handler` against the run VMI: `vm-20261015-cbtf04-r02.18dea13f6ad2c312` at 06:49:55Z (full-pass detach) and `vm-…18dea27bec0700e2` at 07:12:34Z (incremental-pass detach); each event appears twice in the watch stream (ADDED + count/rv update). Message: "failed to mount filesystem hotplug volume …backup-target-pvc: lstat …disk.img: no such file". In both passes the backup had already reached Done=True with a success reason, the attachment pod (`hp-volume-bn45q`, `hp-volume-fc4cn`) was deleted, the volume was unmounted, and the destination PVC remained Bound. Classification: observed anomaly, not a confirmed defect — the events are loud (visible in the event stream) rather than silent corruption, and cleanup demonstrably completed. Engineering follow-up: determine whether the detach path's `lstat disk.img` failure is benign event noise or a real cleanup race. Evidence: `observer/watches/events-20261015-cbtf04-r02.jsonl` (4 HotplugFailed records, 2 distinct event objects); `observer/finding.md` contradictions §2; `ledger.jsonl:16` (Lead verdict reconciliation labels it the product finding).

**P2 — Architectural separation hypothesis confirmed (positive result).**
Deleting the controller leader 17.2 s into the active copy did not interrupt the data plane: the launcher pod never restarted, the copy ran to Done=True in 67 s total, the new leader (`kgtth`, 06:49:24Z) completed reconciliation, cleaned the temp attachment, and advanced the tracker exactly once. This is the Jira issue's expected outcome (`jira-issue.md` Expected Outcome: "separation between the data-copy process and controller reconciliation"). Evidence: criteria 1–8 above; `observer/finding.md` timeline 06:48:50→06:49:55.

`recovery/summary.json` `backups.full.status=PENDING` while the live object is Done=True — traced to the run.json repair (§4-H2), i.e., harness-caused; it is not a CBT behavior. ## 4. Harness findings (test infrastructure, strictly not product)

**H1 — Trigger abort via .env environment leak.**
The launch wrapper sourced `/root/virt-cbt-lab/.env` wholesale (`set -a`), leaking `GUEST_BASE_FILE_COUNT=1000`, `GUEST_FILE_SIZE_MIN_MIB=15`, `GUEST_FILE_SIZE_MAX_MIB=20` and overriding the script's intended defaults (8 × 1024 MiB). The baseline workload therefore ran as 1000 files × 15–20 MiB (17,431 MiB per trigger.log) instead of 8 × 1024 MiB. Post-injection (~06:49:12Z) the trigger worker killed its process group (SIGTERM then SIGKILL, pgid 579156), interrupting `make e2e` mid-vm-backup stage and the observer-internal subshell; exit codes were lost; the scripted incremental follow-up never started. Injection itself had already fired correctly at 06:49:07.697Z, so this did not invalidate the chaos window. Evidence: `trigger/exit-statuses.json` (overall, abort_cause, workload_env_actual vs workload_env_intended_script_defaults); `trigger/trigger.log` pipeline-configuration header (GUEST_BASE_FILE_COUNT=1000). Note: the smaller-but-more-numerous workload still widened the copy window adequately (copy ran 06:48:50→06:49:55), but the deviation from spec-intended sizing is recorded by the Lead as a harness finding (`ledger.jsonl:16`).

**H2 — run.json repair under human approval.**
Because the trigger died before the stage recorded the full backup, LR `run.json` was left at `status=baseline_ready`, `backups.full=null` (preserved verbatim as `run.json.pre-repair-20261015T070811Z`). With user approval (human gate 07:09:10Z, `ledger.jsonl:10`), the Lead repaired `run.json` to `incremental_ready`/complete with backups.full populated from live CR values (checkpoint, PVC Bound 80Gi, success reason), replicating the `scripts/vm-backup.sh:108-119` schema; the incremental follow-up was then run by the RecoveryWorker rather than by the scripted path. Consequences visible in artifacts: `recovery/summary.json` `backups.full.status=PENDING` (stale framework field, §3-P3) and the procedure-deviation note on criterion 10. The repair replicated existing schema from live cluster state and did not fabricate observations — the underlying states were independently proven by observer watches and terminal snapshots.

**H3 — Report-fidelity checker REJECT at revision 1 (resolved at revision 2).**
The first report draft contained two unsupported citations — a reconstructed `virsh checkpoint-list --tree` command line (only the output `recovery/checkpoint-tree.txt` was recorded) and an untraceable "07:16:55Z completion" claim (log terminal time is 07:16:56Z) — plus one checker false positive (workload path `/home/cbt-demo/cbt-workload`, which *is* evidenced in LR `fragments/setup.json`, `report.json`, `workload-manifest.json`). REJECT upheld on items 2–3; single revision loop authorized; revision 2 fixed both and passed. Evidence: `checkers/report-fidelity.json` (revision 2, prior_citations dispositions); `ledger.jsonl:17-18`.

No dedicated watch stream for the incremental vmbackup object (the exact-name vmbackup watch covers the full backup only; incremental terminal state came from post-hoc read-only snapshot `evidence-terminal/incremental-backup-final.json` + namespace events). No observer-side pre-injection checkpoint-tree capture. Restore/hash verification is RecoveryWorker evidence; the observer did not witness it. No `qemu-img info` / `qemu-img map` capture anywhere; the restore criterion was met via file/byte/hash checks only (`recovery/summary.json` scope note: "does not independently inspect qcow2 allocation maps").
