## 3. Product findings (CBT behavior)

**P1 — CBT dirty-block retention: 68GiB copied for 3GiB logical change (non-blocking, CONFIRMED).**
The CBT bitmap tracks blocks written, not live data. Recovery attempt 1's 1000-file plan wrote ~66×1GiB of guest files that were then deleted between checkpoints; those blocks stayed dirty. The retry-3 incremental therefore had to copy ~66+ GiB into a fixed 30Gi destination and **failed with ENOSPC at 10:35:56Z** ("No space left on device", launcher backup.go:332; destination filled to 29GiB — `recovery/rbd-du-backup-volumes.txt:5`). The retry-5 incremental with a 100Gi destination succeeded and **physically copied 68GiB** (rbd-du used_size, `recovery/rbd-du-retry5.txt:5,8`) for a 3GiB logical mutation (2 files added + 1 modified, `recovery/summary.json.copy` incremental_passes[0]); independently corroborated by qemu-img: incremental artifact qcow2 disk size **67.7GiB with backing file rootdisk.qcow2** (`recovery/qemu-img-preserved-artifacts.txt`, `ledger.jsonl:21`). Customer guidance: avoid large write-then-delete churn between checkpoints, or size incremental destinations to peak dirty volume rather than logical change (`reports/test-run-result.md:59`). Expected CBT semantics, but operationally surprising — worth a sizing-guidance ticket.

**P2 — libvirt retained the failed backup's checkpoint after CR deletion (non-blocking, product observation).**
After the approved deletion of the failed incremental CR and its PVC, the libvirt checkpoint tree still contains the failed child `vm-incremental-…-p01-2026-10-15_10-35-19` under the full checkpoint (`recovery/checkpoint-tree-post-retry5.txt:5-9`; pre-cleanup tree capture in `ledger.jsonl:17`). Tree ⊃ live objects; the final tree is full → orphaned failed child → retry-5 child (`ledger.jsonl:19`). The orphan did not block the subsequent successful incremental (fresh timestamp-suffixed checkpoint name, `ledger.jsonl:17`), but it is a leaked domain-level object. Engineering follow-up (`reports/test-run-result.md:60`).

**P3 — HotplugFailed events at post-backup detach (non-blocking, same workflow-typical pattern as r02).**
Observer PRESERVED records HotplugFailed-at-detach matching the r02-success pattern — workflow-typical, not chaos-attributable (`ledger.jsonl:9`; observer/finding.md:65-66). Both passes ended fully correct (Done=True, clean unmount). Not re-graded here; reproduction question belongs to the flow/matrix track.

**Clean product behavior under the actual disruption:** the data-plane copy survived the leader deletion (copy active 09:14:09.971Z → Done 09:15:15Z spanning the 09:14:27Z deletion), failover completed in ~16s, tracker advanced exactly once per backup, attachment cleanup complete, full + incremental restores hash-exact (observer/finding.md:9-15,68-71). ## 4. Harness findings (test infrastructure, strictly not product)

**H1 — Rogue silent-wolf lifecycle from trigger-worker probe self-match.**
The trigger worker's liveness probe `bash -c pgrep -f "make e2e" …` matched its own probe process, fell through to the success branch, sourced the checkout `.env` wholesale (third occurrence of the env-leak class), and launched an unapproved `make e2e` (TYPE=all, run-id 20261015091633-silent-wolf-4eb4, PID 1468693) that held the checkout E2E lock and blocked the r03 incremental stage (exit 2 at 09:18:52Z). The rogue lifecycle ran to completion (~09:26Z) and self-released the lock; human-approved scoped cleanup deleted all silent-wolf resources with exact run-id match; r02/r03 verified intact (`ledger.jsonl:8,10-11`; `trigger/stage-outcomes.jsonl:3-5`). Notably the clean-env guard worked for the actual trigger launch (8 files × 1024MiB baseline) — the leak was in the worker's probe path, not the trigger script (`ledger.jsonl:8`).

**H2 — Incremental-pass sizing spec gap.**
The spec/trigger pin baseline sizing but not incremental-pass sizing, so the checkout `.env` value `GUEST_INCREMENTAL_FILE_COUNT=1000` reached the plan via `make -include .env` — a distinct path from the env-leak class, occurring *with* clean-env launch (`ledger.jsonl:14`). It caused the 1000-file mutation plan (→ P1's dirty blocks) and required the human-approved amendment to 2 files/pass.

**H3 — 5-attempt recovery sequence with 4 Lead/human-gated state interventions.**
The same-VM follow-up needed five attempts: (1) trigger stage blocked by rogue lock; (2) retry-1 failed under the leaked plan; (3) retry-2 blocked by lifecycle state gate; (4) retry-3 ENOSPC (product-adjacent but harness-sized destination, see P1); (5) retry-4 inventory gate; (6) retry-5 PASS — five retry logs preserved (`recovery/incremental-followup*.log/.exit`). Four documented interventions, each user-approved and original-preserving: plan amendment 1000→2 + guest cleanup; run.json status resets (4 resets total, originals `.pre-amend-20261015T102825Z`, `.pre-status-reset-20261015T103413Z`, plus two later, `ledger.jsonl:15,17-18`); failed-CR/30Gi-PVC deletion + manifest 30Gi→100Gi (reverted post-run, `ledger.jsonl:17,19`); guest baseline rollback (sha256-verified, `ledger.jsonl:18`). All downstream gates verified live state, so no fabricated observation — but the recovery needed 4 state interventions to complete, a harness-sequencing cost, not a product defect (`ledger.jsonl:25`, observer/finding.md:72-74).

## 6. Unexpected observations (hypotheses / follow-ups, not graded)

- **U1:** The failed-backup checkpoint surviving CR deletion (P2) suggests libvirt checkpoint lifecycle is owned by the domain, not the backup CR, and is not garbage-collected on backup-object deletion. Hypothesis only from one run; single reproduction.
- **U2:** The incremental destination sizing (30Gi) implicitly assumed logical-change sizing; P1 shows CBT destinations must be sized to the dirty-bitmap extent, which can vastly exceed logical change after churn. Follow-up: sizing guidance in product docs; harness already recorded the spec gap (H2).
- **U3:** Leader failover ~16s (09:14:27Z → 09:14:43.048Z) with copy unaffected is consistent with, but not proof of, clean separation under heavier load — window-position and backend variation remain for later matrix legs (matrix-proposal.md Legs 3–4).
- **U4:** Observer labeled the trigger's internal exit 1 (Krkn SLO exit) separately from product health — a useful pattern: the injection-validity checker correctly classified the Krkn SLO-exit as guard noise (`ledger.jsonl:24`).
