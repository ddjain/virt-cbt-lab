## Decision: Next action = EVIDENCE FIX (physical-delta / qcow2 allocation-map proof of incrementality) — this is **NOT** a chaos leg

**One line:** the next action is an evidence fix, not a chaos leg: capture `qemu-img info --backing-chain` + `qemu-img map` evidence that the post-restart pass-1 image is chained to and allocates only the blocks changed since the recorded full checkpoint, because that is the single open gap on this scenario's *central* claim and it sits exactly on the Jira's named failure mode ("a silent incorrect incremental is a failure"), while every remaining chaos dimension (restart position, guest sizing, VM vs VMI restart, even multiple restarts) either exercises the same code path, has already been varied, or leaves that same residual bounded and therefore fails the marginal-value test.

Rationale (marginal value, explicit):

- **The run's verdict and the residual are specific, not general.** Two blind checkers graded hash-pinned evidence: injection validity PASS (target/window/independent-effect) and evidence sufficiency PASS on all five §5 criteria with **one bounded residual**, named verbatim in `checkers/evidence-sufficiency.json` `criteria[1].detail` ("UNPROVEN (bounded residual): block-e…") and `missing_evidence[0]` ("Block-extent level incrementality of the pass-1 backup (qcow2 allocation map / dirty-bitmap extents)", severity `non-blocking residual`). The deterministic evaluator's `INVALID` is **INAPPLICABLE** (`state.json` `"evaluator":"INVALID (inapplicable, HV1)"`) and is not the run's verdict.
- **The residual is the negation of the Jira's failure mode.** The checker explains why §5.2 still SUPPORTS the criterion: the spec's operative test is "changed blocks vs full — data content correct per restore" and the restored content matches the mutated manifest (2000 files / 36561747968 B / `a9ca19b4…`, `summary.json` `.guest_payload`, `.restore_hashes`). The residual's *only* alternative failure shape, per the same document, is "a self-contained full image mislabelled Incremental" — i.e. precisely the silent wrong incremental the Jira names. So the one thing this scenario cannot yet affirm is the exclusion of its own failure mode; `summary.json` `.scope` admits the mechanism limitation literally ("does not independently inspect qcow2 allocation maps").
- **The harness's own rules call this an open physical claim, not a closed one.** The run's evidence-checker contract (`cbt-chaos/scenarios_v2/CBT-I-01/runs/20261016-cbt-i-01-r01/contracts/check-evidence.md`, named in `checkers/evidence-sufficiency.json` `.contract`) grades as its criterion 1 "The pass after the restart is honest … changed blocks relative to the full"; `.agents/skills/cbt-chaos-run/SKILL.md:204` requires inspecting "the relevant qcow2 backing relationship and allocation metadata (`qemu-img info`/`qemu-img map`) when available" and states that an `Incremental` label or file size alone does not prove the physical delta; `.agents/skills/cbt-chaos-evidence-checker/SKILL.md:42-46` says physical claims need exactly that evidence; `.agents/skills/cbt-chaos-flow-analyst/SKILL.md:64-66` says its absence "is a stated limitation, not a pass".
- **The map is reusable machinery and a precondition for the next leg's value.** Any future I-01 leg's p01 image carries the same residual and would be graded the same way, so a new chaos parameter buys a differently-parameterised run with the same bounded incrementality claim. It also benefits every other incremental scenario in the campaign (F-04/I-04-class) that currently infers the delta from label + duration + restore content.
- **It is cheap, low-risk, and can start with zero new chaos.** No chaos parameter changes and no new failure surface. The method is prior art in this repo: the v1 design of this very scenario already listed `qemu-img info`/`qemu-img map` on the incremental artifact for backing-file/cluster-count comparison (`cbt-chaos/scenarios/04-vmi-restart-between-backups/scenario-spec.md` §5 verification commands; `chaos-plan.md` §H step 3 flags its absence as the pipeline's concrete gap); `RESTORE_HELPER_IMAGE` already provides `qemu-img`/`qemu-nbd` (`README.md:438`, `.env.example:112-116`); the restore-verify pod already mounts the full and p01 PVCs read-only and runs `qemu-img rebase/convert` (`chaos-plan.md` §A/§H); and F-04 r03 proved the physical delta post-mortem with `qemu-img info` on the preserved artifact plus ceph usage (`.agents/skills/cbt-chaos-run/cbt-chaos-run-learnings.md`, 2026-10-15 entry; evidence under `cbt-chaos/scenarios_v2/CBT-F-04/runs/20261015-cbtf04-r03/recovery/`).
- **Cheapest decisive action first, no avoidable cluster cost.** The closed run's backup PVCs may still be Bound (the campaign leaves run resources in place as evidence — e.g. the CBT-I-04 closure note in `cbt-chaos/campaign-progress.md`). If they are, the map is captured against the **already-preserved artifacts with no new lifecycle and no new PVC request** — which matters, because each full+incremental cycle requests large destinations (`summary.json` `.backups.full.pvc_capacity="1489Gi"`) against a shared HostPath pool whose free-space guard must stat the pool mount, not its parent (`cbt-chaos-run-learnings.md`, 2026-10-13 capacity entry). Only if the artifacts are gone or uninspectable does the leg escalate to a fresh identical run.
- **Why not the chaos dimensions first:** restart position is effectively saturated (Leg 1 injected 54 s after the checkpoint was recorded and 119 s before the incremental object; Leg 2 injected 2 s after full `Done` and 89 s before the incremental object — both ends of a stage-ordered, minutes-wide window, `scenario-spec.md` §3); guest sizing cannot change what is exercised because this trigger is stage-ordered and does not race the copy window (unlike F-01/F-04), it would only lengthen the copies; deleting the **VM** object is out of contract (it tears the lifecycle down, `scenario-spec.md` §4) and a *graceful* restart is a different disruption class belonging to a new scenario, not a leg here; and **multiple restarts** is the only genuinely dark in-scope chaos dimension — real, but ranked below Leg 3 and proposed only if a leg budget remains (Leg 4 below).

## Leg 4 (deferred) — multiple restarts before the incremental (the only dark in-scope chaos dimension)

- **Parameters:** identical to Leg 2, except the disruption is applied **2–3 times** before the incremental stage: delete `vmi/vm-<RUN_ID>`, await a new VMI UID reaching Running/Ready (`scenario-spec.md` §6 guard), repeat, and start the incremental stage only after the last recreation is Ready — every deletion strictly after the full `Done` with the tracker holding exactly the full checkpoint, and no incremental object existing throughout.
- **Question:** is checkpoint redefinition **idempotent** across repeated instance replacement — after N restarts does the pass-1 backup still chain to the single recorded full checkpoint with exactly one checkpoint on the object, exactly one tracker advancement, no duplicate/orphaned checkpoint, CBT `Enabled` on the final instance, and restore content still correct?
- **Why deferred:** it is a genuine coverage gap, but its marginal value is lower than Leg 3's (the per-restart code path is already evidenced once, and its incrementality claim would carry the *same* residual until the map exists — see Decision). It also needs a bound: 3 restarts maximum, one leg, no other dimension varied.
- **Expected observation by outcome:** SUCCESS — single chain, one advancement, no duplicate checkpoint, restores PASS, and (with Leg 3 landed) the p01 map still delta-shaped; FAILURE — a second/duplicate checkpoint, a tracker regression, CBT disabled or a full fallback after the second restart, or a covered-data mismatch → product finding, hard stop #1/#5.
- **Preconditions:** Leg 3 landed (so the incrementality claim is gradeable physically); capacity guard passes; fresh RUN_ID/VM; observer armed for the full multi-restart window; the trigger's wait-for-Ready loop bounded.

### Not proposed (and why)

- **Restart position within the gap:** effectively saturated. Leg 1 injected 54 s after the checkpoint was recorded (119 s before the incremental object), Leg 2 injected 2 s after full `Done` (89 s before the incremental object); the window is stage-ordered and minutes wide by design (`scenario-spec.md` §3), so position inside the gap cannot change the mechanism exercised (instance replaced, then recreated, then the incremental stage runs). The one remaining sub-position — a restart *overlapping* the incremental stage start — redefines the window (it breaks §5 criterion 1's ordering) and risks a harness-blocked stage; it needs a spec change, not a leg. Defer.
- **Guest sizing (`GUEST_BASE_FILE_COUNT` / file size):** zero marginal value here. Unlike F-01/F-04 this trigger does not race a copy window — it sequences stages — so widening the copy changes durations only, not the mechanism or any criterion. Drop.
- **VM restart vs VMI restart:** out of the scenario's contract. The Jira's chaos action is "Delete the VMI" and deleting the **VM** object tears down the lifecycle (`scenario-spec.md` §4). A *graceful* restart (guest/domain reboot rather than instance replacement) is a different disruption class with a possibly different checkpoint-redefinition requirement [INFERENCE — not evidenced by any I-01 artifact] and would need its own scenario spec, trigger and criteria. Defer as a new-scenario candidate, not a variation of this one.
- **Trigger's standard evidence artifacts (the Step B additional harness delta) / evaluator shape:** the artifact gap closes no spec §5 criterion (`missing_evidence[2]`, severity `non-blocking`); it is worth landing only because Step B re-runs the chaos path anyway. The evaluator's confidently-wrong `INVALID` is harness finding **HV1** and is fixed on the evaluator side (a declared scenario shape selecting the applicable check set, returning `NOT_APPLICABLE`/`INCONCLUSIVE` for checks outside its model) — not by adding chaos legs. Do not re-litigate HV1 here.

## Hard-stop conditions (Lead enforces; apply to every leg)

1. **Any FAIL verdict** on any leg → matrix stops; findings escalated before further cluster time.
2. **Two consecutive BLOCKED legs** → stop and reassess the harness, not the scenario. (I-01 has no BLOCKED leg: Leg 1 and Leg 2 are both PASS.)
3. **Same-VM post-chaos backup failure** (the incremental pass cannot run on the recovered VM) → stop and preserve resources.
4. **Cluster degradation or capacity starvation** (controller replicas not recovering, PVCs Pending, pool free space below the destination requests) → stop immediately.
5. **Checkpoint/tracker misadvancement** — a duplicate or orphaned checkpoint, a tracker regression, or a checkpoint attributable to a copy that did not complete → stop and file the product defect. (Leg 3's `FAILURE-B` — a self-contained p01 image mislabelled `Incremental` — fires this stop.)
6. **Evidence-integrity stop:** any change to the closed run's frozen pack (`evidence-index.json`, 50 files, sha256 `dfaa18e1…`), or an index regenerated after the last write.
