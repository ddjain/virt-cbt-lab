## What this is, in one paragraph

A changed-block-tracking (CBT) push-mode backup copies a VM's disks into a destination volume that is hot-plugged only while the copy runs. When the copy starts, the backup CR (`VirtualMachineBackup`) records a checkpoint name — the identity of the QEMU checkpoint (the per-disk change-tracking snapshot marking the copied state). When a backup **succeeds**, the chain's tracker CR (`VirtualMachineBackupTracker.status.latestCheckpoint`) is updated with that checkpoint, and the next incremental in the chain uses it as its parent. The originating run observed what a **failed** backup leaves behind: the backup CR reached terminal `Done=True` with a failure reason ("No space left on device") and *still carries* its `checkpointName`, while the tracker's status was never written at all — one object advertises a checkpoint, the chain authority records none. No closed run has ever issued the next backup against a tracker in that state, so the behavior that matters operationally — retry after a failed full, an extremely common production pattern — is unmeasured. This experiment proposes constructing that split state deliberately and then issuing the follow-up backup. It is **not a chaos-injection scenario and not a krknctl scenario**: no fault needs to be injected during a healthy backup; the required precondition is simply a full backup that fails after its copy has started, followed by a follow-up backup against the same tracker.

**When → then → expected**

- **When** a fresh virtual machine's full push-mode `VirtualMachineBackup` has started copying (its `status.checkpointName` is set on the CR) and then fails terminally — `Done=True` with a failure reason — leaving the backup CR's `checkpointName` set while the `VirtualMachineBackupTracker` it targets has an empty/never-written status subresource.
- **And** the follow-up **CBT-EXP-13** is applied: the chain's next backup is created against the same tracker — an incremental `VirtualMachineBackup` in the normal chain progression (a retried full is the sibling variant, see Open questions).
- **Then (current behaviour — unknown, this is the experiment):** no closed run has issued a follow-up backup after a terminally-failed full on this stack. The originating run's harness aborted the pipeline immediately after the failed full (0/1 incremental passes, exit 4, fail-closed by design), so the next-backup behavior is unobserved.
- **Expected behaviour (hypothesis under test):** one of three outcomes — (i) the follow-up correctly rejects or rebases the orphaned checkpoint name (starts a fresh chain, or fails with an explicit, truthful error naming the missing checkpoint); (ii) the follow-up wedges with a checkpoint-not-found / broken-bitmap error, blocking the VM's backup chain until manual intervention; or (iii) the follow-up completes and writes a chain whose parent references the never-recorded checkpoint — a chain-correctness defect whose proof is a restore that fails or restores wrong data.

## Context (for an engineer new to this area)

- **What the feature does** — KubeVirt CBT push-mode backups. A `VirtualMachineBackup` CR copies a VM's disks into a destination PVC hot-plugged only while the copy runs. Each backup is named by a *checkpoint* (the QEMU dirty-bitmap checkpoint marking the copied state); a chain's backups share a `VirtualMachineBackupTracker` CR, whose `status.latestCheckpoint` records the most recent successful checkpoint. An incremental backup copies only the blocks changed since that checkpoint and uses it as its parent.
- **Where the question sits** — the divergence between two status surfaces after a terminally-failed backup. The backup CR's `status.checkpointName` is written early (observed: one resourceVersion after the copy-phase `Progressing=True` flip) and, on failure, is *not* cleared by the terminal write. The tracker's `status.latestCheckpoint` is written only on success (observed: zero tracker writes on the failed run; a successful chain's tracker on the same cluster is populated). A failed backup therefore leaves the backup CR advertising a checkpoint identity that the chain authority never recorded.
- **Observed surface vs. origin** — the orphaned field lives on the *failed* backup CR, but the harm (if any) would surface *later and elsewhere*: on the next backup in the chain (an incremental that cannot resolve its parent) or at restore time (a chain whose parent references a nonexistent checkpoint). A delayed, displaced failure surface is exactly the kind that escapes per-backup health checks.
- **Why it matters** — "full backup failed, retry / continue the chain" is a routine operational sequence. If the follow-up wedges (outcome ii), every failed full blocks the chain until someone manually clears state. If the follow-up chains off the orphan (outcome iii), the defect surfaces at restore time — the worst moment — as a recovery point that does not recover. Even in the resilient case (outcome i), the failed CR's retained `checkpointName` is an observability hazard: an operator or automation reading the backup CR may believe a (partial) recovery point exists when the tracker holds none.

## Expected behaviour (contract)

- **Primary criterion — the follow-up's disposition, graded from raw streams plus chain evidence:** (i) reject/rebase — the follow-up either starts a fresh chain (tracker gains a checkpoint not parented on the orphan) or fails with an explicit error that truthfully names the missing/orphaned checkpoint; (ii) wedge — the follow-up fails with a checkpoint-not-found/broken-bitmap class error and the chain cannot proceed without manual state clearing; (iii) corrupt chain — the follow-up completes and the resulting chain references the orphaned checkpoint as parent (tracker `latestCheckpoint` or captured backing-chain evidence), with restore verification as the decisive check.
- **Verdict mapping (for the future grading owner):** valid split-state construction + outcome (iii) with a failed or wrong restore = FAIL (bug filed with the construction proof); outcome (ii) = product-behavior question — whether chaining off a failed full is contractually expected to work belongs to triage; file a bug only if the wedge contradicts an established contract; outcome (i) = PASS at the achieved n, with the retained-checkpointName observability note recorded as advisory. A follow-up that itself fails on capacity = INCONCLUSIVE for this question (confounded), never graded as a product result.
- **Secondary criteria:** tracker/checkpoint consistency after the follow-up's terminal state (no half-written or duplicate checkpoint); hotplug attachment cleanup on the follow-up (hp-volume pod, VMI hotplug volume status, VolumeAttachment where applicable); restore hashes for whatever chain exists; the follow-up's own terminal condition truthfulness (Done/reason consistency).
- **Validity gates:** the full must have provably reached copy start (a captured resourceVersion carrying both `Progressing=True` and a non-null `checkpointName`) before failing; the failure reason must be recorded; the tracker's emptiness must be verified read-only immediately before the follow-up is issued; the follow-up's terminal state must be graded from raw watch streams, not exit codes; capacity headroom for the follow-up must have been recorded up front. Missing evidence is UNKNOWN, never a silent PASS.

## Impact, workaround and data safety

- **If outcome (iii):** the chain that results restores incorrectly or not at all — a data-protection defect that surfaces at restore time (the worst moment), affecting every retry-after-failed-full sequence. Blast radius per event: one run-scoped backup chain.
- **If outcome (ii):** the VM's backup chain is wedged after a failed full until stale checkpoint state is manually cleared — an availability defect for the backup function, recurring on every failed full.
- **If outcome (i):** the failure-path resilience picture is strengthened, and the remaining issue is the observability hazard of the retained `checkpointName` on failed backup CRs (operators/automation may infer a recovery point that does not exist).
- **Data safety:** no guest-data corruption path is modelled — the originating VM stayed Running with its workload intact, and this proposal injects no fault into a healthy backup. The measured risk is confined to backup-chain correctness, which is precisely the measurement.
- **Workaround:** none claimed and none prescribed. If a wedge or corrupt chain is observed, the fix belongs to product triage (parent selection consulting the tracker rather than the failed CR's field, or clearing `checkpointName` on terminal failure); this proposal does not propose an unverified product fix. Manual state-clearing runbooks are out of scope.
- **Frequency:** every terminally-failed full backup on this stack leaves the split state (single-observation confidence); the follow-up behavior — the thing that decides whether that matters — is what this experiment measures. Retry-after-failure is a routine production pattern, so the answer has direct operational weight.
