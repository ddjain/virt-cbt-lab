## 5. Product findings vs harness findings

### 5.1 CBT product behaviour

**P1 (severity high, confidence high) — A backup whose checkpoint is inconsistent with the QEMU bitmaps is left non-terminal indefinitely instead of failing.**
`vm-incremental-20261016-exp06-r02-p01` was created at 04:29:26Z and remained with `Initializing=True`/`Progressing=False` (reason: its destination PVC "is being attached to VMI …"), no `type`, no `Done`, no `includedVolumes`, no `completionTimestamp`, `resourceVersion 27323776` unchanged, through the last read at 05:0xZ — i.e. ~28+ minutes past creation and past the 20-minute consumer timeout. The only failure surface was repeated `BackupError` warning events plus controller 400s and re-enqueues (~21 over ~28 minutes; 40 controller lines 04:29:29Z → 04:40:22Z). Evidence: `trigger/legB-incremental-backup.yaml#status`; `observer/watches/events.jsonl` (`reason=BackupError`, 21 rows, first 04:29:29Z); `observer/effect/virt-controller-window.log:98,99,103,193,194`; `observer/effect/virt-handler-window.log`; `observer/FINAL.json#runtime_checks_at_final_utc.p01`; `recovery/recovery-report.json#steps[0]`. Caveat carried from `checkers/verdict.json#product_findings[0]`: the observation is solid; attributing it to the removed bitmap leans on the product's own `Code=109` message naming that bitmap plus the injector's (unclosed) provenance.

**P2 (severity high, confidence high) — The checkpoint redefinition silently drops a disk whose bitmap is missing, while the tracker keeps advertising it.**
After the restart, `RedefineCheckpoint` reported success with no warning (`trigger/controller-redefinition-window.log:87`, 04:28:45.625161Z), yet the checkpoint XML contains only `vda` (`observer/effect/checkpoint-dumpxml-post.xml`), while `tracker.status.latestCheckpoint.volumes` still lists `rootdisk` **and** `datadisk` (`trigger/tracker-after-restart.yaml`, rv 27322960; `observer/effect/post-tracker.json`, read 04:50:46Z). **P3 (severity medium, confidence medium) — The VMI's CBT `backupStatus` publishes a checkpoint name that libvirt does not have, and enumerates both volumes for a pass whose backing chain is broken.**
`observer/effect/post-vmi-cbt.json` (captured 04:54:41Z): `changedBlockTracking.state=Enabled`, `backupStatus.checkpointName=vm-incremental-20261016-exp06-r02-p01-2026-10-16_04-29-26`, `volumes=[vda/rootdisk, vdb/datadisk]`; `observer/effect/checkpoint-dumpxml-p01.txt` → "error: Domain checkpoint not found … p01-2026-10-16_04-29-26". ### 5.2 Harness / orchestration behaviour

**H1 (confidence high) — Observer pre-capture design left the run's mandated pre-state witness missing.**
A 10 s sampling cadence against a ~10 s fail-closed window, with the samples that fell inside the window lost to the launcher swap (3 `exec_failed`), meant `observer/effect/qmp-bitmaps-pre.json` does not exist and 0 of 48 history rows report `target_present=true` (`observer/effect/pre-bitmap-history.jsonl`; `observer/PRESERVED.json#bitmap_present_before_removal.gap_explanation`). **H2 (confidence high) — `scenario-verdict.sh` implements a different scenario family.**
It reports `VERDICT=FAIL`, exit 1, `failing_check=injection-signal`, but its table is written for the interrupted-FULL-backup / launcher-pod-kill family (active-copy signal, failed FULL, clean lifecycle). "Reported as returned, not softened", with the applicability limitation recorded (`checkers/verdict.json#sub_verdicts.deterministic_evaluator`; `ledger.jsonl` ev 30).

**H3 (confidence high) — the workflow's 20-minute Done wait turns a stalled product object into a workflow timeout, and the failure is recorded only on the harness side.**
`trigger/trigger.log` ("error: timed out waiting for the condition …" after 20m35s), `run.json#current_incremental_pass.status=failed/#failed_at=04:49:27Z`, `run.json#stage_timings[3]` 1233 s — while the CR itself carries no failure (`checkers/verdict.json#harness_findings[2]`).

**H4 (confidence high) — the staged interface cannot add a same-VM pass after a failed one without destroying the mandated evidence.**
`TYPE=extend` refused verbatim because `lifecycle status is verification_failed`; the only documented unblock (`TYPE=reconcile`) deletes the failed pass's CR/PVC, which the recovery contract forbids (`recovery/step3-extend.log`; `recovery/recovery-report.json#same_vm_check_verdict`; `checkers/verdict.json#harness_findings[3]`). (a) `write-run-summary.sh` is recorded as reporting `cbt.vm_state=PENDING` when the lifecycle verification never ran, which misread as a CBT state and pushed the evaluator's `cbt-recovered` check to UNKNOWN while the live VM/VMI both report `Enabled` (`checkers/verdict.json#harness_findings[6]`); in the two `summary.json` snapshots available to me the field reads `Enabled` (`runs/20261016-exp06-r02/summary.json#cbt.vm_state`, `recovery/summary.json.after#cbt.vm_state`) — I note both and make no contradiction claim (`[INFERENCE]`: the PENDING variant belongs to an intermediate snapshot that was regenerated in place). (b) `exit-statuses.json#control_full_status` is hardcoded `0` in the trigger; the authoritative source is `trigger/trigger.log` ("Leg A full+incremental+verify status: 0") (`trigger/run-notes.md#anomalies 2`). ## 6. If I had to re-run this

1. **Pre-resolve the witness before the surgery, then read the bitmap immediately around the removal.** Bind the checkpoint name and the datadisk QEMU node (`libvirt-2-format`, unique `…/cbt/datadisk.qcow2` + `-format`) *before* the launcher swap, and issue the observer's own QMP `query-named-block-nodes` read seconds before and seconds after `block-dirty-bitmap-remove` — or better, have the observer perform the removal-adjacent reads through a path that survives the swap. Fixes H1/E9 and closes C2's present-before leg (it also removes the reason for `checkers/verdict.json#human_decision_points[0]`).
2. **Make the trigger hold the window open until the observer confirms its pre-read.** The window is currently ~10 s wide and the trigger proceeds on an observer gate that only proves watches are alive, not that the pre-state was captured (`trigger/trigger.log` OBSERVER GATE lines). A rendezvous file whose absence blocks the QMP command converts an unrecoverable evidence gap into a retryable abort.
3. **Width the pass bound and add a terminal-state classifier.** Have the trigger poll the CR for a *terminal* condition (Done or Failed) with a hard cap, and record the non-terminal case as its own first-class outcome (it is the second independent reproduction of the same non-terminal stall, `docs/findings/finding-1-backup-cr-livelock.md` Path A, cited as background only). Today the 20-minute wait records failure on the harness side only (`run.json#current_incremental_pass.status`) and emits no classification line (`trigger/run-notes.md#anomalies 4`) — this is H3 and it is what makes C4 unevaluable.
4. **Add a pass-adding stage that preserves evidence.** A `TYPE=extend` variant that snapshots the failed CR/PVC (or keys on a new pass name) before any reconcile/delete would let C5 be answered without violating the recovery contract's no-deletion rule (H4, `checkers/verdict.json#human_decision_points[1]`).
5. **Free pool capacity first, and measure it on the right filesystem.** Re-run only with the PV_DIR filesystem measured (`/dev/sdb`-style `df` inside the CSI container) and with ≥100 GiB free, or shrink the rootdisk/clone so the forced-full same-VM alternative is affordable (H5, H6, `ledger.jsonl` ev 22).
6. **Rewrite or replace the deterministic evaluator's check table for this scenario family** so that a scenario with no active-copy signal and a successful FULL does not report `FAIL`/`injection-signal` (`verdict-evaluator.json`; H2).
7. **Fix the small bookkeeping defects while in there:** the hardcoded `control_full_status`, the double-counted ready-file gate, the 5-of-7 `pids.json` snapshot, the `PENDING`/`Enabled` `vm_state` reporting, `observer/finding.md`'s handler-log claim, and the ledger-push exclude list that truncated the ledger (H7).
8. **Decide the fsfreeze question before the next run**: fix the guest `/mnt/datadisk` mount/permissions so the control full is a cleanly frozen baseline, otherwise P4 stays unresolved and C1 keeps its caveat (`observer/watches/vmbackup.jsonl.ts`; `observer/effect/post-vmi-cbt.json`).
9. **Author an explicit spec clause for the observed outcome.** The spec's FAIL/RESILIENT wording has no branch for "detected loudly but never terminal"; adding one (e.g. "detected with warning but no terminal condition for T > pass bound → DEFECT: liveness") removes the ambiguity that produced three different reads of the same object (checker UNKNOWN, observer RESILIENT, spec DEFECT/RESILIENT) — see §3.
