# Errata — Lead-authored corrections for CBT-EXP-06 run 20261016-exp06-r02

The closed run's pack is frozen and is NOT rewritten. These corrections were
appended to its ledger as `lead_correction` events and are recorded here; where
they conflict with the pack, these corrections govern.

1. **`checkers/verdict.json#harness_findings[6]` — not reproducible as written.**
   The claim was that `write-run-summary.sh` reports `cbt.vm_state=PENDING` when
   the lifecycle verification never ran. The Lead did observe `PENDING` at
   04:49Z (before the recovery leg's verify stage rewrote the summary), but the
   delivered pack's `runs/20261016-exp06-r02/summary.json` reads
   `cbt.vm_state="Enabled"` (rewritten 10:25:32Z). The finding therefore stands
   only as a *transient* observation, not as a property of the frozen pack.
   Cited by: `cbt-chaos/scenarios_v2/CBT-EXP-06/analysis/20261016-exp06-r02-improvements.md`
   (premise correction a).

2. **`reject-reasons.tsv` row 3 / recovery contract REV 3 — wrong mechanism.**
   The Lead recorded that the harness's documented unblock (`reconcile`) *deletes*
   the failed pass's backup CR and PVC. `scripts/vm-cbt-reconcile.sh` deletes
   nothing: it refuses to reconcile unless the operator has already deleted BOTH
   the failed backup CR and its PVC, and it requires the tracker to still sit on
   the failed pass's checkpoint. The decision to refuse reconcile was still
   correct in effect (the evidence would have to be removed by hand), but the
   attribution was wrong; both the reject index and the follow-up driver's header
   comment now state the verified behaviour.

3. **Workstation mirror staleness (now fixed).** After the post-close ledger
   appends and the final index regeneration, the local mirror was stale (37 ledger
   lines and the pre-checker 151-file index) and failed `pack-validate.sh`. It was
   re-pulled and now validates (`pack-validate: OK`, 42 ledger lines, 157 indexed
   files).

4. **Trigger follow-up (from the same review).** The trigger's
   `exit-statuses.json` carries a hardcoded `control_full_status: 0` (the log line
   is authoritative), the observer gate double-counts ready files (logs 14 for 7),
   `observer/finding.md` line 69's "no virt-handler line" is falsified by 20 handler
   lines, and the run captured no platform version (live value at close:
   OpenShift 4.22.15, k8s v1.35.6 — obtainable with `oc get clusterversion`).
