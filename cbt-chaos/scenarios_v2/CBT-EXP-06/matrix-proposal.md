## 1. LEG 1 — Recommended next leg: repair the tracker (align it with the redefined checkpoint), then take one new pass

**Why this leg and not a re-run:** it is the only route that can produce a *terminal* artifact for the original silent-drop hypothesis without a new full run, it answers principal questions (a) and (b) at once, it discriminates the mechanism that drives the pass's volume list, it re-uses the live wedged state on the same VM, and it is the only leg that fits today's free space without any reclaim. Capacity-wise it costs one 30 GiB incremental destination that — on this pool — costs ≈0 real bytes until data flows (`F3` pre-pass pool reading `43,215,937,536 B` ≈ r02's post-recovery `43,215,941,632 B` despite p01/p02 existing; their destination dirs were `du 0`).

**Hypothesis.**
H1a: the backup request's volume list is derived from `tracker.status.latestCheckpoint.volumes` `[INFERENCE]` — the `Code=109` message names `vdb` although the redefined QEMU checkpoint declares only `vda` (`observer/effect/checkpoint-dumpxml-post.xml`), which is only consistent with the request (not the checkpoint) still carrying `datadisk`. If so, aligning the tracker with the redefined checkpoint lets the pass start, and since the checkpoint now declares only `vda`, the pass should terminate `Done=True` with `includedVolumes=[rootdisk]` and **the datadisk absent** — the original hypothesis confirmed *with a terminal artifact* (the "silent" half then lives in the metadata chain, not in a warning-free completion).
H1b (null): the controller enumerates the VM's disks instead; the pass wedges identically after the repair → the wedge is driven by the QEMU bitmap state, not by the tracker metadata, and "repair the tracker" is **not** a fix (a new operator-runbook fact; weights the product root cause).
H1c: the launcher elects a Full fallback for the invalidated chain → `Done=True type=Full` with both disks (a proven-safe path) — a RESILIENT outcome, not a defect finding.

All three outcomes are decisive and are classed by the driver; none of them can be produced by r02's evidence.

**Exact stage / command shape** (new driver `cbt-chaos/scenarios_v2/CBT-EXP-06/tracker-repair-followup.sh`, modelled on and no larger in scope than `same-vm-followup.sh`; the staged interface cannot be used — it refuses a pass on a `verification_failed` lifecycle and its only documented unblock destroys the evidence, `recovery/step3-extend.log`, H4):

```
  bash cbt-chaos/scenarios_v2/CBT-EXP-06/tracker-repair-followup.sh --plan   # rehearsal: resolves identity, prints the plan, mutates nothing, exit 0
RUN_ID=20261016-exp06-r02 NAMESPACE=vm-cbt-demo KUBECONFIG_PATH="$KUBECONFIG_PATH" \
  bash cbt-chaos/scenarios_v2/CBT-EXP-06/tracker-repair-followup.sh          # the leg
```

Primitives (fail-closed at every step; driver aborts with a distinct exit code):

1. **Rendezvous with a non-injector witness (mandatory first, and the reason r02 was BLOCKED).** The observer (not the driver) captures, into `followup/<RUN_ID>-tracker-repair/`, and writes `…/REPAIR-GO` only when all three reads succeeded:
   - `oc get vmbackuptracker vm-tracker-20261016-exp06-r02 -n vm-cbt-demo -o json` → `status.latestCheckpoint.name` + `volumes`;
   - the checkpoint definition from the launcher: `oc exec <virt-launcher-…> -c compute -- virsh -c qemu:///system checkpoint-dumpxml vm-20261016-exp06-r02 --checkpoint <name>` → must show `vda` **only**;
   - the per-disk bitmap read: `virsh qemu-monitor-command vm-20261016-exp06-r02 --pretty '{"execute":"query-named-block-nodes"}'` → the datadisk node (`node-name` ending `-format`, backing `…/cbt/datadisk.qcow2`) has `dirty-bitmaps: []` while the rootdisk node still holds `<name>`.
   The driver refuses to proceed if `REPAIR-GO` is absent, or if any object contradicts the expected pre-state.
2. **Release the live wedge (approved runbook step, F2-verified).** `oc delete vmbackup vm-incremental-20261016-exp06-r02-p02 -n vm-cbt-demo` — **CR only, its PVC is kept**; record `deletionTimestamp`→disappearance (expect ≈3 s), the finalizer release, and the hotplug detach in `vmi.status.volumeStatus`.
3. **The repair.** `oc patch vmbackuptracker vm-tracker-20261016-exp06-r02 -n vm-cbt-demo --subresource=status --type=merge -p '{"status":{"latestCheckpoint":{"name":"vm-backup-20261016-exp06-r02-2026-10-16_04-27-24","volumes":[{"diskTarget":"vda","volumeName":"rootdisk"}]}}}'` (the CRD declares `subresources: {"status":{}}`; verified read-only), then read back `…-o jsonpath='{.status.latestCheckpoint.volumes[*].volumeName}'` = `rootdisk` immediately, again at +30 s, and once more immediately before step 4. Non-reverting patch is expected: the tracker's `resourceVersion` has been 27322960 unchanged since 04:28:45Z across two wedged passes and one recovery leg (observed) — i.e. no spontaneous status reconciliation.
4. **The new pass.** Apply, from a driver-authored manifest using the workflow's own schema (`f3-new-backup.yaml` shape): `PersistentVolumeClaim vm-incremental-pvc-20261016-exp06-r02-p03` (30Gi, `storageClassName: cbt-demo-hpp`) + `VirtualMachineBackup vm-incremental-20261016-exp06-r02-p03` with `spec.source {apiGroup: backup.kubevirt.io, kind: VirtualMachineBackupTracker, name: vm-tracker-20261016-exp06-r02}` and `spec.pvcName: vm-incremental-pvc-20261016-exp06-r02-p03`, labels `virt-cbt-lab/run-id=20261016-exp06-r02`. 30 GiB is the harness default (`INCREMENTAL_PVC_SIZE` default, `scripts/common.sh:60`) and therefore comparable with p01/p02.
5. **Classify with a terminal-state classifier** (the r02 lesson: the product object, not the harness clock, defines the outcome). Poll every 15 s for ≤20 min, recording the CR's `status.type`, `conditions[type=Done].{status,reason,message}`, `status.includedVolumes`, `metadata.resourceVersion`, `deletionTimestamp`; plus namespace events, CR-scoped events, `vmi.status.changedBlockTracking.backupStatus`, VMI `volumeStatus`, virt-controller / virt-handler windows, and pool free per poll. Terminal classes: `SILENT-DROP-CONFIRMED` (H1a) · `CHAIN-RECOVERED` (Done with both disks) · `TERMINAL-MISSING-WEDGE` (no terminal condition by the bound; same 109 signature) (H1b) · `TERMINAL-FAILED` (a `Failed` condition appears — new behaviour for this path) · `FULL-FALLBACK` (H1c).

**Expected observation / evidence.** For H1a: `Done=True`, `type=Incremental`, `includedVolumes=[rootdisk]` only, with the *absence* of any warning naming the datadisk in the pass's own status → the scenario's FAIL (defect) signal, now terminal and gradable; plus (b) answered: the wedge does resolve when the tracker is repaired rather than discarded. For H1b: p03 wedges again with the same 109 line and no terminal condition → (b) answered negatively and H1a refuted. Either way the leg closes the C4/E7 "no terminal artifact" gap for the corrupt-checkpoint path in the scenario's own terms.

**What would make it invalid** (recorded as such, never graded as product behaviour): (i) no non-injector pre-state witness (the r02 reject class) — ungradable; (ii) the tracker patch is reverted by a controller before the pass starts (the manipulated variable was never in effect); (iii) the destination is under-sized for a Full fallback (30 GiB vs an 80 GiB disk) and the pass stops on ENOSPC — an environmental limit, not product evidence (the fallback itself must still be recorded); (iv) a hotplug mount from a previous pass is still attached when p03 is created (interference: the driver must assert `volumeStatus` has no `…backup-target-pvc` entry); (v) the classification rests on namespace/VMI events only, with no CR-scoped capture at the poll cadence — at least as weak as r02; (vi) any run-root artifact under `runs/20261016-exp06-r02/` is modified (forbidden; the leg writes only under `followup/<RUN_ID>-tracker-repair/`).

**Capacity.** One 30 GiB destination PVC request; ~0 real bytes on this pool until data flows (observed: r02's p01/p02 destinations `du 0`; F3's pool reading ≈ unchanged). Free space available: **40.248 GiB today, no reclaim needed** ✓. Guards carried from `same-vm-followup.sh`: refuse to create the pass below 25 GiB free, abort the wait below 8 GiB free, sample free space on every poll. A worst case in which the destination fully allocates 30 GiB leaves ~10 GiB — above the abort guard but under the start guard; therefore the sampler is a hard requirement, not a nicety. Measure with `oc exec -n openshift-cnv <hostpath-provisioner-csi pod> -c hostpath-provisioner -- df -B1 /cbt-demo-pool-data-dir/csi` — **/dev/sdb**, not the `/dev/sda4` filesystem preflight reported (H5).

**Stop conditions for Leg 1.** Global stops (§4) apply, plus: a second hotplug leak appears on this VM (two wedged passes' mounts attached simultaneously) → stop, do not stack further passes; free space <8 GiB during the wait → abort the wait; the VM/VMI leaves Running/`CBT Enabled`, or the datadisk qcow2 is reported corrupt → stop immediately; the tracker patch cannot be verified durable at +30 s → invalid, stop, no classification.

## 2. Ordered follow-ups (≤4 legs total; the dependency order below is the proposed order)

### Leg 2 (after Leg 1) — Tracker-discard chain reset on the same VM (finding-1's matrix row for the *corrupt-checkpoint* path, question (a)'s other route)

The datadisk therefore returns to the chain and the protection loss does not persist into a later full → the *completion-with-datadisk-missing* variant is reachable only through Leg 1 (metadata repair), not through the discard route. This row is currently unverified for the corrupt-checkpoint path (r01 only verified it for the deleted-tracker path; r02's own recovery leg was refused, H4).

- **Stop.** Global stops, plus: more than one disk on the VM (invalid harness); the pre-state witness missing (invalid); `SILENT-DROP` (a Done=True pass missing the only disk) → escalate immediately as a new high-severity variant; a second wedge on a single-disk VM → stop, escalate, and re-scope the ticket's severity.

## 4. Hard stop conditions (Lead enforces; global, then per leg)

Global, applicable to every leg: (1) **any FAIL verdict** on any leg → matrix stops, findings escalate before further cluster time; (2) **two consecutive BLOCKED legs** → stop and reassess the harness, not the scenario; (3) **same-VM recovery failure** (the post-pass follow-up cannot run on the VM) → stop, preserve resources, ask; (4) **cluster degradation** (controller replicas not recovering, PVCs stuck Pending, node pressure, CNV pod count dropping from the 120 baseline) → stop immediately; (5) **capacity starvation** (free space below the leg's named requirement + 25 GiB guard at creation, or below 8 GiB during a wait) → stop/abort, do not shrink destinations to squeeze in; (6) any forbidden mutation (`make clean-all`, `STAGE_SKIP_PREFLIGHT=true`, touching a closed run's pack) → stop and escalate.

Per leg: **Leg 1** — invalid-patch verdict at +30 s; non-injector witness absent; two simultaneous hotplug leaks on the VM; VM/VMI leaves Running/`CBT Enabled`; destination ENOSPC on a Full fallback (record as environmental, stop the pass). **Leg 2** — wedged CR surviving the pre-step; the new pass not a `Full`; the `spec.source … in progress` rejection recurring (the VM-wide deadlock persisting after a tracker reset). **Leg 3** — more than one disk on the VM, or no single unambiguous `-format` node carrying the bitmap (invalid); Debian profile never reaches `CBT Enabled` (3a invalid → use 3b); a Done=True pass missing the only disk → escalate as a new high-severity variant. **Leg 4** — the pre-state witness missing again → leg invalid, harness fix before any further run; evaluator still reporting `injection-signal` FAIL without an applicability record → report faithfully, do not soften.
